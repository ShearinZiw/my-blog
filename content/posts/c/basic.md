## 局变量和局部变量的区别​
### 定义位置不同​
1.全局变量​
◦ 定义在 函数外部，通常在文件顶部​
◦ 整个程序中都可以访问（受 extern / static 影响）​
2.局部变量​
◦ 定义在 函数内部或代码块内部​
◦ 只能在定义它的作用域内使用​

### 作用域不同​
1.全局变量​
◦ 作用域：从定义处到文件结束​
◦ 可被多个函数访问​
2. 局部变量​
◦ 作用域：所在的函数或 {} 代码块​
◦ 离开作用域即不可访问​

### 生命周期不同​
1.全局变量​
◦ 生命周期：整个程序运行期间​
◦ 程序开始时分配，程序结束时释放​
2.局部变量​
◦ 生命周期：函数执行期间​
◦ 函数调用时创建，函数返回时销毁​

### 存储位置不同​
1.全局变量​
◦ 存储在 全局/静态存储区（.data / .bss）​
2.局部变量​
◦ 一般存储在 栈区​
◦ static 局部变量存储在静态区​

### 初始化规则不同​
1.全局变量​
◦默认初始化为 0（未显式初始化）​
2.局部变量​
◦ 不会自动初始化，值为随机值​

### 使用注意点​
1.全局变量​
◦ 优点：使用方便、共享数据简单​
◦ 缺点：​
▪ 破坏模块封装​
▪ 容易引发命名冲突​
▪ 不利于多线程安全​
2.局部变量​
◦ 优点：​
▪ 作用范围小，安全性高​
▪ 有利于代码维护和复用​

### 总结​
​
全局变量作用域大、生命周期长，存放在静态区；局部变量作用域小、生命周期短，通常存放在栈区，未初始化时值不确定。​
​

## 内存分布模型

![](/img/3a701f56-e2c4-44ee-b7f2-26605b2fa9b9.png)

### 先说结论​
1.代码段：存放程序的机器指令（即二进制代码）。通常是只读的，因为程序的指令在执行过程中不应该被修改。​
2.数据段：存放已初始化的全局变量和静态变量。这些变量在程序开始运行时已经赋予了初始值。​
3.BSS 段：存放未初始化的全局变量和静态变量。它们在程序开始运行时会自动初始化为0或者空指针（初始化为0也是在这里）。​
4.堆区：动态分配的内存空间，用于存放程序运行时动态申请的内存。（程序员可以通过函数（如malloc、calloc等）或者操作系统提供的接口来申请和释放堆内存，堆从低地址向高地址增长。）​
5.栈区：存放函数的局部变量、函数参数值以及函数调用和返回时的相关信息。栈区是按照“先进后出”的原则进行管理，内存的分配和释放是自动进行的，栈从高地址向低地址增长。是一块连续的空间。​
6.共享区：也称为文件映射或共享内存，用于实现不同进程之间的内存共享。​
7.只读数据段：存放常量的​

### 代码区（Text Segment）​
存放内容：​
• 可执行指令​
• 只读常量字符串（部分系统）​
特点：​
• 只读​
• 多个进程可共享​
• 防止程序被意外修改​

### 只读数据区（RODATA）​
存放内容：​
• 字符串常量​
• const 修饰的全局常量（可能）​
特点：​
• 只读​
• 编译期确定​
• 位于代码区附近​

### 全局/静态区（Data Segment）​
#### （1）已初始化全局区（.data）​
存放内容：​
• 已初始化的全局变量​
• 已初始化的静态变量​
示例：​

``` C
int g_val = 10;​
static int s_val = 5;
```
​
#### （2）未初始化全局区（.bss）​

存放内容：​
• 未初始化或初始化为 0 的全局变量​
• 未初始化或初始化为 0 的静态变量​
特点：​
• 程序启动时自动清零​
• 不占可执行文件空间​

### 堆区（Heap）​
存放内容：​
• 动态分配的内存​
管理方式：​
• 程序员手动申请和释放​
• 容易产生内存泄漏​
示例：​
​
代码块​

``` C
int *p = (int *)malloc(sizeof(int));​
```

特点：​
• 向高地址增长（一般）​
• 生命周期由程序员控制​

### 栈区（Stack）​
存放内容：​
• 局部变量​
• 函数参数​
• 返回地址​
特点：​
• 自动分配和释放​
• 空间有限​
• 向低地址增长（一般）​
示例：​
​
代码块​

```C
void func() {​
    int a = 10;​
}​
```

### 内存分布示意（逻辑结构）​
​

 │   栈区      │​
 ├────────────┤​
 │   堆区      │​
 ├────────────┤​
 │  .bss      │​
 ├────────────┤​
 │  .data     │​
 ├────────────┤​
 │ rodata     │​
 ├────────────┤​
 │ 代码区      │​
 └────────────┘​
低地址​
​
### 总结​
• 全局变量和静态变量存放在全局/静态区​
• 局部变量存放在栈区​
• malloc/new 申请的内存在堆区​
• const 变量位置与修饰方式、编译器有关​
• 栈快、堆灵活，但栈空间有限​
• 内存分布模型体现了程序中不同数据的生命周期和管理方式，是理解指针、作用域、内存泄漏和嵌入式底层开发的基础​

## 初始化为 0 的全局变量
初始化为 0 的全局变量存储位置：BSS 还是 Data？​

### 全局变量存储区概述​
• Data 段：存储已初始化的全局变量和静态变量。​
• BSS 段：存储未初始化的全局变量和静态变量，或者初始化为 0 的全局变量。​
1.3.2

### BSS 段和 Data 段的区别​
• BSS 段：存储未显式初始化的变量或者初始化为零的变量。​
    ◦ 它在程序加载时会自动初始化为 0。​
    ◦ 不占用实际磁盘空间，程序运行时由操作系统为它分配空间。​
    ◦ 优点是节省了程序文件的存储空间，程序文件中没有将所有零值写入磁盘，只记录了该变量的存在。​
• Data 段：存储已显式初始化的全局变量。​
    ◦ 包括非零初始化的全局变量和静态变量。​
    ◦ 在程序加载时，操作系统会将这些值加载到内存中。​

### 初始化为 0 的全局变量的存储位置​
• 初始化为 0 的全局变量会存储在 BSS 段。​
◦ 这种做法是为了节省程序的存储空间，因为 BSS 段中的内存会被操作系统自动初始化为 0。​
•未初始化的全局变量也是存储在 BSS 段，并且会默认初始化为 0。​
​
### 存储位置总结表​
​
​
### 为什么要把初始化为 0 的全局变量放在 BSS？​
• 节省存储空间：在可执行文件中，BSS 段的变量不会将 0 值存储到磁盘上，这样可以减少文件大小。程序加载时，操作系统会自动将这些变量初始化为 0，避免了程序需要在磁盘中存储零值。​
• 高效加载：BSS 段中的变量在程序加载时自动初始化为 0，这使得操作系统可以更高效地管理内存。​

### 总结​
​
初始化为 0 的全局变量会被存储在 BSS 段，而已显式初始化（非零）的全局变量会存储在 Data 段。BSS 段的优势是节省存储空间，因为它不会在程序文件中保存零值，而是由操作系统在程序加载时自动初始化。​

## 函数参数压栈顺序（Calling Convention）

### 调用约定简介
调用约定决定：

- 参数如何传递（寄存器 or 栈）
- 参数压栈顺序
- 栈由谁清理
- 返回值如何传递

常见调用约定：`__cdecl`、`__stdcall`、`__fastcall`。

---

### __cdecl 调用约定（C/C++ 默认）

#### 1. 参数压栈顺序
- **从右到左压栈**

```c
foo(a, b, c);
// 压栈顺序：c → b → a
```

#### 2. 栈清理方式
- **调用者清理栈**

```asm
call foo
add esp, 12   ; 调用者清理参数
```

#### 3. 返回值
- 使用 **EAX** 返回

#### 4. 特点
- 支持可变参数（如 printf）
- C/C++ 默认调用约定

---

### __stdcall 调用约定（WinAPI 常用）

#### 1. 参数压栈顺序
- **从右到左压栈**（与 __cdecl 相同）

#### 2. 栈清理方式
- **被调用者清理栈**

```asm
ret 12   ; 被调用者清理参数
```

#### 3. 返回值
- 使用 **EAX**

#### 4. 特点
- Windows API 大量使用
- 不支持可变参数

---

### __cdecl vs __stdcall（核心区别）

| 项目 | __cdecl | __stdcall |
|------|---------|-----------|
| 参数压栈顺序 | 右 → 左 | 右 → 左 |
| 栈清理 | 调用者 | 被调用者 |
| 可变参数 | 支持 | 不支持 |
| 常用场景 | C/C++ 默认 | WinAPI |

一句话：

> **__cdecl 调用者清栈，__stdcall 被调用者清栈。**

## 如何在 C 中实现位域映射寄存器？

### 位域结构定义

假设寄存器结构如下：

```
| CONTROL(16bit) | STATUS(8bit) | DATA(8bit) |
```

可用位域映射：

```c
#pragma pack(1)
typedef struct {
    unsigned int control : 16;
    unsigned int status  : 8;
    unsigned int data    : 8;
} Register;
```

---

### 寄存器映射

```c
#define REGISTER_BASE_ADDRESS 0x40000000
typedef volatile Register* RegisterPtr;

int main() {
    RegisterPtr reg = (RegisterPtr)REGISTER_BASE_ADDRESS;

    reg->control = 0x1234;
    reg->status  = 0x56;
    reg->data    = 0x78;
}
```

---

### 关键点（面试必问）

#### 1. `volatile`
寄存器值随时可能变化，必须强制每次从内存读取。

#### 2. 对齐问题
寄存器映射必须 **无填充字节**，因此：

- 使用 `#pragma pack(1)`
- 或 `__attribute__((packed))`

#### 3. 位域顺序依赖编译器
不同编译器对位域排列方式不同：

- 与 CPU 大端/小端无关
- 与编译器实现有关

因此：

> **位域不能用于跨平台通信协议，但适合 MCU 寄存器映射。**

## 函数中申请堆内存的注意点

### 明确内存所有权（最重要）
- 函数内 `malloc/new` 分配的堆内存 **不会随函数结束自动释放**
- 必须明确：
  - **谁申请**
  - **谁释放**
- 常见约定：
  - 函数申请 → **调用者释放**
  - 在接口文档中明确说明释放责任

一句话：

> **堆内存必须有人负责释放，否则一定会泄漏。**

---

### 正确传出堆内存指针

#### 1）作为返回值（合法）
```c
int* func() {
    int *p = malloc(sizeof(int));
    return p;   // OK
}
```

#### 2）通过二级指针传出
```c
void func(int **p) {
    *p = malloc(sizeof(int));
}
```

---

### 不能返回局部变量地址（经典错误）
```c
int* func() {
    int a;
    return &a;   // ❌ 栈变量，函数结束即失效
}
```

原因：

- 局部变量在 **栈区**
- 函数返回后栈帧销毁 → 指针变成 **悬空指针**

---

### 必须检查 malloc 返回值
```c
int *p = malloc(100);
if (p == NULL) {
    return;  // 内存不足必须处理
}
```

避免因内存不足导致崩溃。

### 避免内存泄漏

常见错误：

```c
p = malloc(100);
p = malloc(200);   // ❌ 原来的 100 字节泄漏
```

原则：

> **新分配前，旧内存必须先 free。**


### 释放后避免悬空指针
```c
free(p);
p = NULL;
```

防止：

- 重复释放
- 访问已释放内存


### 函数失败路径必须释放内存
```c
p = malloc(100);
if (error) {
    free(p);
    return;
}
```

所有 return 路径都必须处理内存，否则泄漏。


### 作用域 ≠ 生命周期
- 指针变量在函数内  
- **堆内存的生命周期独立于函数**

函数结束后：

- 指针变量销毁  
- 但堆内存仍然存在（除非被释放）


### 嵌入式开发的额外注意点
- **不要在中断中 malloc/free**
- 避免频繁申请/释放（会导致碎片）
- 优先使用：
  - 静态内存
  - 内存池（Memory Pool）
  - 预分配缓冲区

一句话：

> **嵌入式中尽量避免动态内存，必须用时也要严格管理生命周期。**


### 总结

- 函数中申请的堆内存不会自动释放，必须明确释放责任  
- 不能返回局部变量地址  
- malloc 必须检查返回值  
- 所有路径都要 free，避免泄漏  
- free 后置 NULL，避免悬空指针  
- 嵌入式中尽量避免动态内存  

一句话：

> **函数中申请堆内存的核心是：能正确传出、有人负责释放、失败不泄漏、释放后不再使用。**

## malloc/free 使用时可能出现的问题

### 内存泄漏（Memory Leak）
**现象：** 分配的堆内存没有被释放，导致程序占用内存不断增加。

**原因：**
- `malloc/calloc` 后忘记 `free`
- 中途 return 或异常路径未释放
- 指针被覆盖导致无法释放

**示例：**
```c
int *p = malloc(100);
// 忘记 free → 泄漏
```

**解决：**
- 每个 malloc 必须有对应 free
- 失败路径也要释放
- 使用工具检测（valgrind/ASan）

---

### 双重释放（Double Free）
**现象：** 同一块内存被 free 两次，导致未定义行为（崩溃、堆损坏）。

**示例：**
```c
int *p = malloc(10);
free(p);
free(p);  // ❌ 双重释放
```

**解决：**
```c
free(p);
p = NULL;
```

---

### 悬挂指针（Dangling Pointer）
**现象：** 指针指向已释放的内存，再次访问会导致崩溃或数据错误。

**示例：**
```c
int *p = malloc(10);
free(p);
*p = 5;  // ❌ 悬挂指针访问
```

**解决：**
- free 后置 NULL
- 避免返回局部变量地址

---

### 内存不足（Out of Memory）
**现象：** malloc 返回 NULL，但程序未检查，导致访问 NULL 指针崩溃。

**示例：**
```c
int *p = malloc(1000000000);
*p = 1;  // ❌ p 可能为 NULL
```

**解决：**
```c
int *p = malloc(100);
if (!p) return;
```

---

### 未初始化内存
**现象：** malloc 分配的内存内容是未定义的，直接使用会产生不可预期结果。

**示例：**
```c
int *p = malloc(sizeof(int));
printf("%d", *p);  // ❌ 未初始化
```

**解决：**
- 使用 `calloc`
- 或手动初始化

---

### 内存访问越界（Out-of-bounds Access）
**现象：** 访问超出分配范围的内存，导致堆损坏、崩溃。

**示例：**
```c
int *p = malloc(10 * sizeof(int));
p[10] = 5;  // ❌ 越界（有效范围 0~9）
```

**解决：**
- 严格检查数组边界
- 分配前确认大小计算正确

---

### 内存碎片化（Memory Fragmentation）
**现象：** 多次 malloc/free 导致堆空间不连续，无法分配大块内存。

**常见于：**
- 长时间运行的服务
- 频繁分配/释放不同大小的内存

**解决：**
- 使用内存池（Memory Pool）
- 尽量减少频繁分配/释放
- 使用固定大小块

---

### 总结

malloc/free 常见问题包括：

1. **内存泄漏**：忘记 free  
2. **双重释放**：free 两次  
3. **悬挂指针**：free 后继续使用  
4. **内存不足**：未检查 malloc 返回值  
5. **未初始化内存**：malloc 得到垃圾值  
6. **越界访问**：访问超出分配范围  
7. **内存碎片化**：频繁分配释放导致堆不连续  

一句话：

> **malloc/free 的核心风险是：不释放、重复释放、越界访问、未初始化、碎片化。正确管理生命周期是关键。**


## static 关键字（C & C++）

### static 在 C 中的用法

#### 1. 局部静态变量（static local variable）
- **作用域**：仅在函数内部  
- **生命周期**：整个程序运行期间  
- **存储位置**：静态区（.data / .bss）  
- **初始化**：只初始化一次，默认值为 0  
- **典型考点**：多次调用函数时变量值保持不变  

#### 2. 修饰全局变量（static global variable）
- **作用域**：仅限当前源文件  
- **链接属性**：内部链接（internal linkage）  
- **用途**：避免跨文件访问，减少命名冲突  
- **嵌入式常见**：模块化封装  

#### 3. 修饰函数（static function）
- **作用域**：仅限当前源文件  
- **用途**：模块化、隐藏实现细节  
- **嵌入式驱动中非常常见**

### static 在 C++ 中的扩展用法

#### 1. 静态成员变量（static member variable）
- 属于类本身，而非对象  
- 所有对象共享  
- 必须在类外定义一次  

#### 2. 静态成员函数（static member function）
- 无 `this` 指针  
- 只能访问：  
  - 静态成员变量  
  - 静态成员函数  
- 可通过类名直接调用  

#### 3. 静态局部对象（static local object）
- **首次调用时构造**  
- **程序结束时析构**  
- 常用于 **单例模式**（Meyers Singleton）

### C vs C++ static 对比总结

| 特性 | C | C++ |
|------|----|------|
| 局部 static | 保持状态 | 同 C |
| 全局 static | 限制作用域 | 同 C |
| static 函数 | 文件内可见 | 同 C |
| 类内 static | 无 | ✔ 扩展：类级共享成员 |

### 嵌入式常见使用场景
- 限制变量/函数作用域（模块封装）  
- 避免命名冲突  
- 保存函数内部状态（如计数器）  
- 单例外设驱动对象（C++）


### static 注意点
- static 改变的是 **作用域** 或 **生命周期**  
- static ≠ const  
- 静态变量默认初始化为 0  
- C 的 static 用于作用域/生命周期控制  
- C++ 扩展到类级共享成员

## typedef 与 #define 的区别

### 核心区别
| 项目 | typedef | #define |
|------|---------|----------|
| 本质 | 类型别名 | 预处理文本替换 |
| 参与编译 | ✔ | ✘（仅文本替换） |
| 调试器可见 | ✔ | ✘ |
| 类型检查 | ✔ | ✘ |

### 基本用法
```c
typedef unsigned int u32;   // 类型别名
#define U32 unsigned int    // 文本替换
```

### 对指针的影响（高频考点）

#### typedef（整体作为类型）
```c
typedef char* PCHAR;
PCHAR a, b;   // a、b 都是 char*
```

#### #define（简单替换）
```c
#define PCHAR2 char*
PCHAR2 c, d;  // c 是 char*，d 是 char
```

**原因：typedef 定义的是“类型”，而宏只是替换文本。**

### 对 const 的影响（高频易错）

#### typedef
```c
typedef int* PINT;
const PINT p;   // int* const p
```
- p 是 **常指针**  
- 指向内容可变  

#### #define
```c
#define PINT2 int*
const PINT2 p;  // const int* p
```
- p 是 **指向常量的指针**  
- 指针可变，内容不可变  


### 调试与可读性
- typedef  
  - 调试器可识别  
  - 提高可读性  
- #define  
  - 调试不可见  
  - 出错信息不直观  

### 适用场景建议

#### 使用 typedef
- 定义复杂类型（如函数指针）  
- 提高可读性  
- 跨平台类型适配  
- 指针、结构体、函数指针  

#### 使用 #define
- 常量定义  
- 条件编译  
- 宏函数（需谨慎）  


### 注意点
- 不用 #define 定义类型（无类型检查）  
- typedef 不能定义变量  
- 宏替换无类型概念  
- typedef 是类型别名，参与编译；宏在预处理阶段替换

## const 关键字

### 基本含义
- const 用于限定变量为只读  
- 本质是 **编译期语义约束**  
- 不保证放入 ROM（与编译器/链接脚本相关）  
- 中断、指针搭配是高频考点  

### 修饰普通变量
```c
const int a = 10;
```
- a 不能被修改  
- 必须在定义时初始化  
- 具有类型检查特性  

### 修饰指针（重点必考）

#### 指向常量的指针（pointer to const）
```c
const int *p;
int const *p;
```
- 不能通过 p 修改内容  
- 指针本身可变  

#### 常指针（const pointer）
```c
int * const p = &a;
```
- 指针不可变  
- 内容可变  

#### 指向常量的常指针（const pointer to const）
```c
const int * const p = &a;
```
- 指针不可变  
- 内容不可变  

### const 与数组
```c
const char s[] = "abc";
```
- 数组元素不可修改  
- 常用于字符串常量保护  

### const 与函数参数
```c
void func(const int *p);
```
- 防止函数内部误修改数据  
- 提高接口安全性与可读性  
- 嵌入式驱动中常见  

### const 与全局变量
```c
const int g = 10;
```
- 默认具有内部链接（internal linkage）  
- 跨文件使用需 `extern const`  
- 常放在只读存储区（依赖编译器/链接脚本）  

### const 在 C++ 中的补充
- 可修饰成员函数  
- 可用于区分重载  
- 与 C 的语义不同（如 const 成员函数修饰隐式 this 指针）  

### const 注意点
- const 修饰的是 **离它最近的对象**  
- const ≠ #define  
- C89 中 const 变量不能作为数组大小  
- const 可与指针、数组、函数参数组合使用  
- const 的核心价值：**只读语义 + 接口安全性**  


## 指针与引用

### 指针（Pointer）的定义
概念：指针是一个变量，用于存储另一个变量的地址。

```c
int a = 10;
int *p = &a;
```

特点：
- 本身占用内存  
- 可以为空（NULL）  
- 可以改变指向  
- 需要显式解引用 `*p`  

### 引用（Reference）的定义（C++）
概念：引用是已有变量的别名，本质上是受限的指针。

```cpp
int a = 10;
int &r = a;
```

特点：
- 必须初始化  
- 不能为空  
- 一旦绑定不可再改变指向  
- 使用方式与普通变量一致  

### 内存层面理解（常考）
- 指针：有独立存储空间  
- 引用：通常通过指针实现，但对用户透明  

```cpp
sizeof(int*) != sizeof(int&)
```

### 使用场景

#### 指针适用场景
- 动态内存管理  
- 需要表示“无对象”  
- 多态、复杂数据结构  

#### 引用适用场景
- 函数参数传递（避免拷贝）  
- 操作符重载  
- 提高代码可读性  

### 典型函数参数对比
```cpp
void func1(int *p);
void func2(int &r);
```
- 指针：需判空  
- 引用：更安全、语义更清晰  

### 指针注意点
- 未指向时初始化为 NULL，避免野指针  
- 指针类型必须与目标类型匹配  
- 释放内存后将指针置空，避免悬挂指针  
- 动态内存分配后需检查是否成功，避免越界访问
