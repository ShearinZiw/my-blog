## OSI 七层模型

### **1. 概念**
- OSI（Open Systems Interconnection）由 **ISO** 提出  
- 目标：实现不同厂商设备互联  
- 将网络通信划分为 **7 层**，每层负责特定功能  
- 特点：**分层、独立、协作、模块化**


### **2. 七层模型逐层总结（自下而上）**

#### **① 物理层（Physical Layer）**
**核心职责：传输比特流（0/1）**  
- 定义电气特性、接口规范、信号电压、速率  
- 不关心数据含义，只负责“电信号”传输  

**典型：** 网线、光纤、RJ45、电压电流

#### **② 数据链路层（Data Link Layer）**
**核心职责：将比特流封装成帧，实现相邻节点可靠传输**  
- 差错检测（CRC）  
- 流量控制、帧同步  

**典型：** MAC 地址、以太网、ARP

#### **③ 网络层（Network Layer）**
**核心职责：逻辑寻址 + 路由选择**  
- 决定数据包从源到目的的路径  
- 跨网络转发  

**典型：** IP 地址、IP 协议、路由协议



#### **④ 传输层（Transport Layer）**
**核心职责：端到端通信**  
- 数据分段、重组  
- 提供可靠或不可靠传输  

**典型：** TCP（可靠）、UDP（实时）、端口号



#### **⑤ 会话层（Session Layer）**
**核心职责：建立、管理、终止会话**  
- 会话状态控制  
- 同步、恢复  

**典型：** 会话管理、断点续传（概念）



#### **⑥ 表示层（Presentation Layer）**
**核心职责：数据格式转换**  
- 编码、加密、解密、压缩  
- 屏蔽不同系统的数据表示差异  

**典型：** ASCII、UTF-8、压缩、SSL/TLS（概念上）



#### **⑦ 应用层（Application Layer）**
**核心职责：为用户和应用提供网络服务接口**  
- 定义应用协议  

**典型：** HTTP/HTTPS、FTP、SMTP、DNS、SSH



### **3. OSI 七层模型总结**
1. 分层设计降低复杂度  
2. 每层职责明确  
3. 工程中更常用 TCP/IP，但 OSI 是理论基础  



## TCP/IP 四层模型 — 工程实践模型

### **1. 基本概念**
- 互联网实际使用的模型  
- 比 OSI 更简化、更贴近工程  
- 四层结构：**网络接口层 → 网络层 → 传输层 → 应用层**



### **2. 四层模型逐层总结**



#### **① 网络接口层（Network Interface Layer）**
**核心职责：在物理网络上传输数据**  
- 定义帧格式、MAC、介质访问方式  
- 屏蔽硬件差异  

**典型：**以太网、ARP、MAC 地址



#### **② 网络层（Internet Layer）**
**核心职责：逻辑寻址 + 路由转发**  
- 提供无连接、不可靠的数据报服务  

**典型：**IP、ICMP、路由协议



#### **③ 传输层（Transport Layer）**
**核心职责：端到端通信**  
- 使用端口号区分应用  
- 决定可靠性  
- 实现端到端的通信，保证数据从源主机传到目标主机的应用进程
  - 端口管理：标识不同应用进程​
  - 可靠传输（TCP）：顺序、重传、校验、流量控制​
  - 不可靠快速传输（UDP）：低延迟、广播/组播​
  - 多路复用：一个主机可同时处理多个连接

**典型：**TCP、UDP



#### **④ 应用层（Application Layer）**
**核心职责：为应用提供网络服务**  
- 包含 OSI 的会话层 + 表示层功能  
- 为用户和应用程序提供网络服务接口
- 解决的问题：​
    - a. 定义应用数据格式（如 HTTP、FTP、MQTT）​
    - b.提供不同应用间通信协议（文件传输、远程控制、消息传递）​
    - c.数据表现和语义处理（编码、压缩、序列化等

**典型：**HTTP、FTP、DNS、SMTP、SSH



### **3. OSI vs TCP/IP 对应关系（面试常考表）**

| TCP/IP | 对应 OSI |
|--|--|
| 应用层 | 应用层 + 表示层 + 会话层 |
| 传输层 | 传输层 |
| 网络层 | 网络层 |
| 网络接口层 | 数据链路层 + 物理层 |



### **4. TCP/IP 四层模型总结**
1. 更简洁，贴近实际网络协议  
2. OSI 用于理论，TCP/IP 用于工程  
3. 面试重点：**四层职责 + 典型协议 + 与 OSI 的对应关系**



### 最终总结
- **OSI 七层：物理、链路、网络、传输、会话、表示、应用（自下而上）**  
- **TCP/IP 四层：网络接口、网络、传输、应用**  
- **TCP/IP 应用层 = OSI 的应用 + 表示 + 会话**

## 子网掩码（Subnet Mask）

### **1. 基本概念**
- 子网掩码用于 **划分 IP 地址的网络部分和主机部分**  
- 与 IP 地址配合使用，用来判断：  
  **一台主机属于哪个子网**
- 作用：
  - 网络分段  
  - 提高管理效率  
  - 节省 IP 地址

### **2. 原理（核心机制）**

#### **IP 地址 = 网络号 + 主机号**

#### **子网掩码由连续的 1 和连续的 0 组成：**
- **1 → 网络位**
- **0 → 主机位**

#### **示例解析**

**IP 地址：**192.168.1.10  
**子网掩码：**255.255.255.0  

二进制表示：

| 项目 | 二进制 |
||--|
| IP | 11000000.10101000.00000001.00001010 |
| 掩码 | 11111111.11111111.11111111.00000000 |

计算：

- **网络号 = IP & 子网掩码 = 192.168.1.0**
- **主机号 = IP & (~子网掩码) = 0.0.0.10**

### **3. 子网掩码的功能**

#### **① 区分网络和主机**
- 网络号相同 → 同一子网  
- 网络号不同 → 不同子网

#### **② 划分子网**
- 将大网络拆成多个小子网  
- 提高管理灵活性、减少广播域

#### **③ 确定广播地址**
- **广播地址 = 网络号 + 全 1 的主机位**  
- 用于子网内部广播

### **4. 常用子网掩码（CIDR 表示法）**

| CIDR | 子网掩码 | 主机数量 |
||--|--|
| /24 | 255.255.255.0 | 254 |
| /16 | 255.255.0.0 | 65534 |
| /8 | 255.0.0.0 | 16777214 |

说明：  
**“/24” 表示掩码有 24 位 1**

### **5. 总结**
- **子网掩码用来区分 IP 的网络部分和主机部分**  
- **1 表示网络位，0 表示主机位**  
- **通过子网掩码可以判断 IP 属于哪个子网，并确定广播地址**



## MAC 地址与 IP 地址的区别

### 1. MAC 地址（物理地址）

#### **概念**
- MAC（Media Access Control）地址是 **网卡的物理地址**
- 出厂时由厂家写入，通常不会改变
- **长度：48 位（6 字节）**
- **格式：**`XX:XX:XX:XX:XX:XX`
- **工作层：数据链路层（OSI 第 2 层）**
- **作用：在同一局域网内唯一标识设备**

### 2. IP 地址（逻辑地址）

#### **概念**
- IP 地址是网络中的 **逻辑地址**
- 可由管理员手动配置或由 DHCP 动态分配
- **IPv4：32 位**  
- **IPv6：128 位**
- **工作层：网络层（OSI 第 3 层）**
- **作用：标识设备在网络中的位置，实现跨网络通信**



### 3. MAC vs IP — 核心区别对比

| 对比项 | MAC 地址 | IP 地址 |
|--|-|-|
| 类型 | 物理地址 | 逻辑地址 |
| 长度 | 48 位 | IPv4：32 位；IPv6：128 位 |
| 分配方式 | 厂家烧录 | 手动配置 / DHCP |
| 是否可变 | 基本不变 | 可随网络环境变化 |
| 工作层次 | 数据链路层 | 网络层 |
| 作用范围 | 局域网内唯一标识设备 | 跨网络寻址与路由 |
| 是否可路由 | ❌ 不能跨网段 | ✔️ 可跨网段路由 |
| 示例 | `AA:BB:CC:DD:EE:FF` | `192.168.1.10` |

### 4. MAC 与 IP 在通信中的配合（非常重要）

#### **实际通信流程**
a. 应用层生成数据  
b. 网络层使用 **IP 地址** 确定目标网络  
c. **ARP 将目标 IP → MAC 地址**  
d. 数据链路层使用 **MAC 地址** 完成帧传输  

### **一句话总结：**
> **IP 决定“去哪”，MAC 决定“送给谁”。**

### 5. 嵌入式系统中的实际应用

#### 常见场景
- STM32 + LWIP  
- 工业以太网设备  

#### 常见面试追问

##### ❓ **为什么换 IP 不影响局域网通信？**
- 因为 **MAC 地址没变**，交换机仍能识别该设备

##### ❓ **为什么不能只用 MAC 地址通信？**
- MAC 地址 **不能跨网段路由**  
- 路由器只看 IP，不看 MAC



### 6. 总结
> **MAC 地址用于局域网内的物理寻址（数据链路层），IP 地址用于跨网络的逻辑寻址（网络层），两者通过 ARP 协同完成通信。**

## TCP 三次握手（Three-way Handshake）

### 1. 基本概念
- TCP 是 **面向连接、可靠传输** 的协议  
- 三次握手用于 **建立连接**  
- 目的：
  1. **确认双方都具备收发能力**  
  2. **同步序列号（ISN）**，保证可靠传输  



### 2. 三次握手过程（逐步解析）

#### **① 客户端 → 服务器：SYN**
- 客户端发送 **SYN** 报文，请求建立连接  
- 报文中包含客户端的初始序列号 **ISN(c)**  
- 服务器收到后，知道客户端想建立连接  



#### **② 服务器 → 客户端：SYN + ACK**
- 服务器回复 **SYN + ACK** 报文  
  - **ACK = ISN(c) + 1**：确认收到客户端的 SYN  
  - **SYN**：服务器也要建立连接，并发送自己的 **ISN(s)**  
- 客户端收到后，知道服务器同意建立连接且具备发送能力  



#### **③ 客户端 → 服务器：ACK**
- 客户端发送 **ACK** 报文  
  - **ACK = ISN(s) + 1**：确认收到服务器的 SYN  
- 至此，连接建立成功，双方进入 **ESTABLISHED** 状态，可以开始数据传输  



### 3. 三次握手关键点（面试必问）

#### **① 为什么需要三次？（可靠性）**
- 确认双方都能 **发送** 和 **接收**  
- 同步双方的 **初始序列号**  
- 防止旧连接报文干扰新连接  



#### **② 状态转换（常考）**
##### 客户端：
- CLOSED → **SYN_SENT** → **ESTABLISHED**

##### 服务器：
- LISTEN → **SYN_RECEIVED** → **ESTABLISHED**



#### **③ 防止旧连接干扰**
- TCP 使用序列号（ISN）区分不同连接  
- 即使旧报文重传，也不会被误认为新连接  



### 4. 总结
> **TCP 三次握手：客户端 SYN → 服务器 SYN+ACK → 客户端 ACK，用于确认双方收发能力并同步序列号，确保可靠通信。**

## 为什么 TCP 需要三次握手，而不是两次

### 背景
TCP 是面向连接、可靠传输的协议。建立连接的核心目标包括：

- 双方都能发送与接收数据  
- 同步双方的初始序列号（ISN），避免旧连接报文干扰新连接  



### 两次握手的问题
假设只进行两次握手：

1. 客户端发送 SYN  
2. 服务器回复 SYN-ACK  
3. 连接直接建立  

这样会产生以下问题：

- 客户端 **无法确认** 服务器的 SYN 是否到达  
- 如果网络中存在 **旧的 SYN-ACK 报文** 被误认为新连接：  
  - 服务器会误以为客户端已确认连接  
  - 客户端实际上并未收到该 SYN-ACK  
  - 可能导致旧连接的数据被误用，造成数据错乱  

两次握手无法确保双方收发能力，也无法避免旧报文干扰。



### 三次握手如何解决问题
第三次握手（客户端发送 ACK）完成了关键确认：

- 客户端确认服务器的 SYN 已成功到达  
- 双方的初始序列号同步  
- 双方都确认自己与对方具备收发能力  
- 避免旧连接报文导致的错误连接  

因此，三次握手是确保 TCP 连接可靠性的最小次数。



### 可优化的机制
- **TCP Fast Open（TFO）**：在握手过程中携带部分数据，减少首包延迟  
- **长连接（Keep-Alive）**：减少频繁建立连接的开销，提高通信效率  



### 总结
三次握手的第三次 ACK 是必不可少的，它确保双方序列号同步、确认收发能力，并防止旧连接报文干扰。两次握手无法满足这些可靠性要求，因此 TCP 必须使用三次握手来建立连接。


## TCP 的四次挥手

### 基本概念
- 四次挥手（Four-way Handshake）是 TCP 断开连接的标准流程  
- 目的是确保双方数据都发送完毕后再关闭  
- TCP 是全双工通信，发送和接收方向独立，因此关闭需要双方分别确认  



### 四次挥手过程
以下假设 **客户端主动关闭**，服务器被动关闭。

#### 第一次挥手（客户端 → 服务器：FIN）
- 客户端发送 FIN，表示“我已经没有数据要发送了”  
- 客户端进入 **FIN_WAIT_1**

#### 第二次挥手（服务器 → 客户端：ACK）
- 服务器收到 FIN 后回复 ACK  
- 服务器进入 **CLOSE_WAIT**  
- 客户端进入 **FIN_WAIT_2**  
- 此时服务器仍可继续发送数据

#### 第三次挥手（服务器 → 客户端：FIN）
- 服务器数据发送完毕后，发送 FIN  
- 服务器进入 **LAST_ACK**

#### 第四次挥手（客户端 → 服务器：ACK）
- 客户端收到 FIN 后发送 ACK  
- 客户端进入 **TIME_WAIT**  
- 服务器收到 ACK 后关闭连接  



### 关键点
#### 全双工通信
- TCP 的发送和接收方向独立  
- 关闭连接需要分别关闭两个方向，因此需要四次挥手  

#### 状态转换
- 客户端：FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED  
- 服务器：CLOSE_WAIT → LAST_ACK → CLOSED  

#### TIME_WAIT 的作用
- 确保服务器收到最后的 ACK  
- 防止旧报文影响后续新连接  



### 总结
TCP 四次挥手通过 FIN 和 ACK 分别关闭双方的发送方向，确保数据传输完整后安全关闭连接。



## 为什么 TCP 断开连接是四次挥手，而不是三次

### 背景
- TCP 是全双工通信：双方都可以独立发送数据  
- 断开连接必须确保双方的数据都发送完毕  
- 与建立连接不同，关闭连接需要分别确认双方的发送方向是否结束  



### 两次或三次挥手的问题

#### 如果只两次挥手
- 客户端发送 FIN，服务器 ACK 后直接关闭  
- 问题：服务器可能还有未发送的数据，直接关闭会导致数据丢失  

#### 如果只三次挥手
- 客户端 FIN → 服务器 ACK → 服务器 FIN  
- 客户端可能在未确认服务器 FIN 的情况下关闭  
- 存在服务器最后的数据未被客户端确认的风险  



### 四次挥手的必要性
1. 客户端发送 FIN：表示客户端发送方向结束  
2. 服务器 ACK：确认收到客户端的 FIN  
3. 服务器发送 FIN：表示服务器发送方向结束  
4. 客户端 ACK：确认服务器 FIN，双方安全关闭  

由于 TCP 的发送方向是独立的，双方都必须发送 FIN 并收到对方的确认，因此需要四次。



### 总结
TCP 断开连接必须分别关闭双方的发送方向，每一方都需要发送 FIN 并收到 ACK。  
因此，四次挥手是确保全双工通信安全关闭的最小次数，而不是三次。
