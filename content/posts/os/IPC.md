# 进程通信与并发问题

IPC 题的重点不是背七种 API，而是回答四件事：**传什么、谁同步、谁拥有、失败后怎样恢复**。

## 先给选择框架

| 需求 | 常见选择 | 关键边界 |
| --- | --- | --- |
| 父子进程字节流 | 匿名管道、`socketpair` | 管道通常单向；`socketpair` 全双工 |
| 无亲缘本机进程 | Unix domain socket、FIFO | 是否需要请求/响应、传递 fd |
| 结构化小消息 | POSIX / System V 消息队列 | 队列上限、优先级、满队列策略 |
| 大块数据低拷贝 | 共享内存 + 同步原语 | 数据一致性和崩溃恢复由应用负责 |
| 文件与进程共享视图 | `mmap` | 刷盘语义不等于并发同步 |
| 跨主机通信 | TCP / UDP socket | 协议 framing、重连、幂等 |
| 异步通知 | signal、eventfd | 通知通常不承载业务数据 |

选择顺序：先定通信域和消息语义，再定拷贝成本；不要因为共享内存“快”就默认使用它。

## 管道、FIFO 与 socketpair

- `pipe()` 返回两个文件描述符，天然适合有亲缘关系的进程；字节流没有消息边界。
- FIFO 在文件系统中有名字，让无亲缘进程会合；打开时机和对端退出必须处理。
- `socketpair(AF_UNIX, SOCK_STREAM, ...)` 是本机全双工流，能统一到 `poll/epoll`，Unix domain socket 还可传递凭据和文件描述符。

高频追问：一次 `write` 是否对应一次 `read`？对字节流不保证。应用必须自己定义定长头、长度字段或分隔符，并处理半包。

## 消息队列

消息队列保留消息边界，适合小型命令与事件。它并不自动解决所有可靠性问题：

- 队列满时阻塞、丢弃还是覆盖？
- 消费者崩溃后消息是否仍在？
- 同一业务是否允许重复执行？
- 生产速度长期高于消费速度时，背压放在哪里？

工程回答应包含队列深度的来源、超时策略、监控指标和过载降级，而不只是函数名。

## 共享内存

共享内存减少进程间数据复制，但把复杂度转移给应用：

1. 先创建和映射区域；
2. 定义稳定布局、版本号和边界；
3. 用进程共享互斥量、信号量、futex 或无锁协议同步；
4. 明确发布/消费的内存顺序；
5. 处理创建者或持锁者异常退出；
6. 最后解除映射并回收名字/对象。

`volatile` 不能建立线程间 happens-before，不能代替锁或 C 原子操作。它主要约束编译器对该对象访问的优化，常用于 MMIO 等场景。

## 竞态与原子性

竞态是结果依赖不可控执行顺序；数据竞争是不同执行流并发访问同一内存，至少一次写，且缺少同步。在 C/C++ 内存模型中，数据竞争会导致未定义行为。

```c
// “读—改—写”不是因为变量可单次读写就自动原子
counter++;
```

修复方式取决于要保护的不变量：

- 单个计数可用原子 read-modify-write；
- 多字段一致性通常需要互斥锁；
- 条件变化用条件变量，并始终在循环中重新检查谓词；
- 跨进程同步原语必须显式配置为 process-shared。

## 死锁、活锁、饥饿

### 死锁

多个执行流永久等待彼此持有的资源。经典四条件是互斥、占有且等待、不可剥夺、循环等待。破坏任一条件即可预防，工程上常采用全局锁顺序、缩小持锁区和超时/检测。

### 活锁

执行流仍在运行并反复让步，但系统没有业务进展。随机退避、明确仲裁者或限制重试次数可以打破同步节奏。

### 饥饿

某个执行流长期得不到资源，而系统整体仍有进展。需要检查调度策略、公平性、优先级和长期持锁者。

## 条件变量为什么要循环等待

```c
pthread_mutex_lock(&mutex);
while (!queue_has_data()) {
    pthread_cond_wait(&cond, &mutex);
}
consume_one();
pthread_mutex_unlock(&mutex);
```

原因不只是假唤醒：被唤醒到重新拿锁之间，条件可能已被另一个消费者改变。条件变量是“状态可能变化”的通知，不是状态本身。

## 项目追问

- 为什么不用共享内存？请比较消息大小、频率、开发复杂度和崩溃恢复。
- 队列写满怎么办？若答案只是“不会满”，需要给容量计算和压力数据。
- 对端重启后怎样重新同步状态？是否有版本、序号、心跳和幂等键？
- 谁负责关闭 fd、`unlink` FIFO / shm？异常路径是否泄漏？
- 怎样定位偶现卡死？至少要有线程栈、锁等待、系统调用和心跳证据。

## 卡死诊断剧本

1. 先区分 CPU 忙还是全部睡眠：`top -H`、`ps -L`；
2. 用 `strace -f -tt -p PID` 看是否卡在 futex、read、write 或 poll；
3. 用调试器获取所有线程栈，画等待关系；
4. 检查 fd、管道/队列容量和对端存活；
5. 若高 CPU 且无进展，检查重试循环和活锁；
6. 加入操作超时、队列水位、消息序号与锁等待时长后复现；
7. 修复后用故障注入验证对端崩溃、队列满和乱序退出。

## 30 秒回答

> IPC 选择不能只看吞吐。字节流适合通用连接，但应用要处理消息边界；消息队列保留边界但有容量和背压；共享内存拷贝少，却必须自行解决同步、内存顺序、布局版本与异常恢复。并发问题先明确共享不变量，再用原子或锁建立同步关系，`volatile` 不能替代它们。
