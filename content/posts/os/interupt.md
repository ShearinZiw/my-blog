# 中断

> 范围说明：下文谈“不能睡眠”的部分主要指 Linux hardirq / MCU ISR 这类原子上下文。Cortex-M 异常优先级、RTOS `FromISR` 边界和 Linux threaded IRQ 的规则并不相同，不能把一套结论机械套到所有平台。可对照 [MCU 主干]({{< relref "../embedded/mcu.md" >}})、[RTOS 主干]({{< relref "../embedded/rtos.md" >}}) 与 [Linux 驱动主干]({{< relref "../embedded/linux-driver.md" >}})。

## 中断上下文（Interrupt Context）

中断上下文是指 **CPU 在处理中断（硬件中断或软件中断）时所处的特殊执行环境**。  
在这个环境中，CPU 会暂停当前进程/线程，转而执行中断服务例程（ISR）。

hardirq / ISR 是约束严格的原子执行上下文，但“最高优先级”并非跨平台事实：中断控制器可配置优先级、屏蔽与嵌套，NMI 等异常还可能高于普通 IRQ。

---

### 4.19.1 中断上下文的特点

#### 1. 实时性强
- 中断必须 **立即响应** 外设事件（如网卡、定时器、中断控制器）。
- ISR 必须 **短小精悍**，尽快退出，避免影响系统实时性。

#### 2. 非阻塞（不能睡眠）
在中断上下文中 **绝对不能阻塞**，包括：

- 不能 sleep / msleep
- 不能等待锁（mutex、semaphore）
- 不能执行可能阻塞的 I/O
- 不能调用 schedule()

原因：  
阻塞会导致中断无法结束，系统无法继续调度，严重影响稳定性。

#### 3. 不允许调度
- 中断上下文中 **调度被禁止**。
- ISR 不能主动让出 CPU，也不能被调度器切走。

#### 4. 重入与嵌套取决于平台
- 同一中断源是否会在处理期间再次进入，取决于控制器、触发方式、ack/mask 时机与内核实现，不能默认“一定不可重入”。
- 高优先级中断可能抢占低优先级 ISR；共享状态必须按目标平台规则保护。

---

### 4.19.2 中断上下文的执行流程

#### 1. 中断发生
硬件设备或软件触发 IRQ。

#### 2. 保存当前进程状态
CPU 保存：

- PC（程序计数器）
- 寄存器
- 内核栈指针

这些信息用于中断返回后恢复执行。

#### 3. 执行中断处理程序（ISR）
ISR 负责：

- 读取设备寄存器
- 清除中断标志
- 将数据放入缓冲区
- 通知下半部（如软中断、tasklet、workqueue）

#### 4. 恢复原任务
ISR 完成后：

- 恢复寄存器
- 恢复 PC
- 返回到被中断的进程继续执行

---

### 4.19.3 中断上下文 vs 进程/线程上下文

| 对比项 | 中断上下文 | 进程/线程上下文 |
|--------|------------|------------------|
| 是否可阻塞 | ❌ 不可阻塞 | ✔ 可阻塞 |
| 是否可调度 | ❌ 不可调度 | ✔ 可调度 |
| 是否有进程身份 | ❌ 无（不属于任何进程） | ✔ 有 |
| 是否切换地址空间 | ❌ 不切换 | ✔ 可能切换 |
| 执行时间要求 | 必须短 | 可长 |
| 典型用途 | 处理硬件事件 | 执行用户任务 |

一句话总结：

> **hardirq 不具备可睡眠的任务语义，不能调用可能阻塞的接口；处理应保持有界，并把耗时工作延后。**

---

### 4.19.4 中断上下文中的注意事项

#### 1. 禁止阻塞操作
不能执行：

- malloc / kmalloc(GFP_KERNEL)
- mutex_lock
- semaphore P 操作
- 文件 I/O
- 网络发送
- sleep / msleep
- schedule()

原因：  
阻塞会导致中断无法结束，系统卡死。

---

#### 2. 不能调用可能触发调度的函数
例如：

- `yield()`
- `sched_yield()`
- `wait_event()`
- `down()`（信号量 P 操作）

这些都会导致调度，而中断上下文禁止调度。

---

#### 3. 中断嵌套与优先级
- 不要假定同一中断天然不可重入，应检查具体控制器与处理流程。
- 某些系统允许高优先级中断打断低优先级 ISR。
- 过度嵌套会导致系统抖动、延迟增加。

---

### 4.19.5 总结（面试高频版）

- **hardirq 不是可睡眠的进程上下文，普通 IRQ 的优先级也不是无条件高于所有异常。**
- **不能阻塞、不能调度、不能睡眠、不能获取可能阻塞的锁。**
- **ISR 必须短小精悍，复杂逻辑应放到下半部（softirq、tasklet、workqueue）。**
- **中断上下文切换不涉及进程切换，因此没有页表切换。**

一句话记忆：

> **中断上下文：不能睡、不能等、不能调度，只能快。**



## 中断和异常的区别

中断（Interrupt）和异常（Exception）都是让 CPU 暂停当前执行并跳转到特定处理程序的机制，但它们的**触发来源、处理方式、同步性、可屏蔽性、恢复方式**都不同。

### 4.20.1 定义

#### 中断（Interrupt）
- **外部事件触发**
- 来自硬件设备（键盘、网卡、定时器、磁盘等）
- 用于通知 CPU 处理外设事件

#### 异常（Exception）
- **内部事件触发**
- 来自 CPU 执行指令时的错误或特殊情况
- 如除零、缺页、非法指令、段错误

一句话记忆：

> **常见术语中，外部 IRQ 通常异步于当前指令；同步异常由当前指令触发。但不同 ISA 对 interrupt / exception 的总称和分类不同。**

---

### 4.20.2 触发来源

| 类型 | 触发来源 |
|------|----------|
| **中断** | 外部硬件设备（异步） |
| **异常** | CPU 执行指令时检测到错误（同步） |

---

### 4.20.3 处理机制

#### 中断处理机制
- 暂停当前任务
- 保存现场
- 执行 ISR（中断服务例程）
- 处理完后返回原任务

特点通常是**异步**；能否屏蔽、延迟或嵌套取决于中断类型与体系结构。

---

#### 异常处理机制
- 当前指令执行失败
- CPU 立即跳转到异常处理程序
- 可能终止程序或修复错误

同步异常与当前指令相关，但可以是可恢复事件（如缺页），也可能转成信号或终止任务；是否可屏蔽要看具体异常类型。

---

### 4.20.4 响应时机

#### 中断
- **异步**
- 可以在任何时刻发生，与当前指令无关

#### 异常
- **同步**
- 必然发生在某条指令执行时

例如：

- 除零 → 在除法指令执行时触发
- 缺页异常 → 在访问内存指令执行时触发

---

### 4.20.5 例子

#### 中断例子
- 定时器中断（时钟滴答）
- 网卡中断（收到数据包）
- 磁盘中断（I/O 完成）

#### 异常例子
- 除零异常
- 段错误（非法内存访问）
- 缺页异常（Page Fault）
- 非法指令（Invalid Opcode）

---

### 4.20.6 优先级与控制

#### 中断
- 通常有优先级，是否嵌套由控制器和软件配置决定
- 普通 IRQ 往往可屏蔽，但 NMI 等不可屏蔽中断是反例

#### 异常
- 同步异常、fault、trap 和系统调用入口的屏蔽与恢复规则各不相同
- 异常处理过程中仍可能发生更高优先级异常或中断

---

### 4.20.7 是否可屏蔽

| 类型 | 可屏蔽？ |
|------|----------|
| **中断** | 普通 IRQ 常可屏蔽；NMI 等不可屏蔽 |
| **异常** | 取决于异常类型和体系结构，不能一概而论 |

---

### 4.20.8 是否可恢复

#### 中断
- **可恢复**
- ISR 执行完后返回原任务继续执行

#### 异常
- **视情况而定**
  - 缺页异常 → 可恢复（加载页面后继续执行）
  - 除零、段错误 → 通常不可恢复（程序终止）

---

### 4.20.9 总结对比（最适合背诵）

| 对比项 | 中断（Interrupt） | 异常（Exception） |
|--------|-------------------|-------------------|
| 触发来源 | 外部设备 | 程序内部错误 |
| 同步性 | 异步 | 同步 |
| 是否可屏蔽 | 取决于 IRQ 类型 | 取决于异常类型 |
| 是否可恢复 | ✔ 通常可恢复 | 部分可恢复 |
| 典型用途 | 处理外设事件 | 处理程序错误 |
| 响应时机 | 任意时刻 | 某条指令执行时 |
| 是否与当前指令相关 | ❌ 无关 | ✔ 强相关 |
| 嵌套 | 由优先级与配置决定 | 可能被更高优先级异常/中断打断 |

一句话总结：

> **面试先说明目标架构：外部 IRQ 常异步，同步异常与当前指令相关；屏蔽、嵌套与恢复能力必须按具体类型回答。**



## 为什么 hardirq / ISR 不应做耗时操作？

中断处理函数会占用受约束的原子上下文，并增加同级/低级中断和任务的响应延迟。
它的核心目标是：

> **快速响应硬件事件，尽快退出，恢复正常调度。**

因此，ISR 中绝对不能执行耗时操作。下面是详细原因。

---

### 4.21.1 阻塞系统其他中断的响应

- ISR 执行期间，CPU 会屏蔽同级或低优先级中断。
- 如果 ISR 执行太久，会导致：
  - 其他中断无法及时响应
  - 中断丢失
  - 系统实时性下降

在实时系统中，这会直接导致 **任务超时、数据丢失、系统不稳定**。

---

### 4.21.2 影响主程序执行

- ISR 会打断当前正在执行的任务。
- 如果 ISR 执行时间过长：
  - 主程序被长时间挂起
  - 系统响应变慢
  - 整体吞吐量下降

ISR 的时间越长，对整个系统的性能影响越大。

---

### 4.21.3 可能导致栈溢出

- ISR 使用 **内核栈**（嵌入式系统中栈空间通常很小）
- 耗时操作往往意味着：
  - 深层函数调用
  - 大量局部变量
  - 复杂逻辑

这些都会增加栈使用量，可能导致 **栈溢出 → 系统崩溃**。

---

### 4.21.4 中断嵌套与优先级阻塞

- 某些系统允许高优先级中断打断低优先级 ISR。
- 如果低优先级 ISR 执行太久，会导致：
  - 若更高优先级中断被屏蔽或平台不允许该嵌套，会形成更长的中断延迟；这不是经典的任务优先级反转
  - 中断嵌套过深，系统抖动严重

这会破坏系统的实时性。

---

### 4.21.5 调度延迟

- ISR 执行期间 **调度器被禁止运行**。
- 如果 ISR 执行太久：
  - 任务调度被延迟
  - 实时任务无法按时执行
  - RTOS 的时序被破坏

在实时系统中，这可能导致 **任务超时、系统失效**。

---

### 4.21.6 可能导致死锁或资源竞争

ISR 中不能执行：

- mutex
- semaphore P 操作
- sleep/wait
- 文件 I/O

因为这些操作可能阻塞，导致：

- 死锁
- 资源竞争
- 系统状态不可预测

ISR 必须是 **无锁、无阻塞、无等待** 的。

---

### 4.21.7 影响系统可维护性与可扩展性

- ISR 过长、逻辑复杂，会让系统难以维护。
- 未来添加新功能时，ISR 的复杂度会进一步增加。
- 复杂 ISR 会成为系统瓶颈，难以扩展。

---

### 4.21.8 避免耗时操作的建议

#### ✔ 1. ISR 必须短小精悍
只做最必要的事情：

- 清除中断标志
- 读取关键寄存器
- 将数据放入缓冲区

#### ✔ 2. 耗时操作放到“下半部”
常见下半部机制：

- SoftIRQ
- Tasklet
- Workqueue
- RTOS 的 deferred interrupt handler

#### ✔ 3. 使用标志位或信号量通知主线程
ISR 中只做：

```c
flag = 1;
```

主线程再处理复杂逻辑。

#### ✔ 4. 避免动态内存分配
如 `malloc()`、`new`，因为：

- 耗时
- 可能阻塞
- 可能导致碎片

#### ✔ 5. 避免阻塞操作
包括：

- sleep
- wait
- mutex
- 文件 I/O
- 网络 I/O

---

### 4.21.9 总结（面试高频版）

> **ISR 应保持有界，因为长处理会增加中断与调度延迟、扩大栈和并发风险；耗时工作应转移到任务、threaded IRQ 或 workqueue 等合适上下文。**

一句话记忆：

> **ISR：不能睡、不能等、不能算太久，只能快。**


## 中断上下文中能否使用互斥锁？

### 中断上下文的特点

- 中断上下文是 CPU 处理中断时的特殊执行环境
- **不能阻塞**
- **不能调度**
- **必须快速执行**
- **重入与嵌套规则由平台决定**

---

### 互斥锁的工作原理

- 如果锁被占用，线程会 **阻塞等待**
- 阻塞意味着调度器需要切换线程
- 互斥锁依赖 **调度机制**

---

### 为什么中断上下文不能使用互斥锁？

#### 1. 互斥锁可能阻塞（中断不能阻塞）
如果 ISR 获取互斥锁失败，它会阻塞等待锁释放，但：

> **中断上下文不能阻塞，否则整个系统会卡死。**

#### 2. 可能导致死锁
场景：

- 线程 A 持有 mutex
- 中断发生，中断处理程序也尝试获取 mutex
- ISR 阻塞等待线程 A
- 线程 A 无法运行（被中断打断）

→ **死锁**

#### 3. 中断上下文不能调度
互斥锁依赖调度器，而 ISR 中调度器被禁止。

#### 4. 锁的 API 必须匹配执行上下文
普通 mutex 依赖可调度睡眠语义，因此不能用于 hardirq。能否使用自旋锁、关本地中断或 RTOS 临界区，要按共享者所在上下文和平台 API 选择。

---

### 正确做法

#### ✔ 使用原子操作（推荐）
适合简单计数、标志位：

```c
atomic_inc(&counter);
```

#### ✔ 禁用中断（短时间）
用于保护极短的临界区：

```c
local_irq_disable();
// critical section
local_irq_enable();
```

#### ✔ 使用自旋锁（spinlock）
内核中断上下文常用：

```c
spin_lock_irqsave(&lock, flags);
// critical section
spin_unlock_irqrestore(&lock, flags);
```

特点：

- 不阻塞
- 忙等
- 可用于中断上下文

---

### 总结

> **中断上下文绝不能使用互斥锁，因为互斥锁会阻塞，而中断上下文不能阻塞。**

正确方式：

- 原子操作
- 自旋锁（带 irqsave）
- 禁用中断（短时间）

一句话记忆：

> **ISR：不能睡、不能等、不能锁，只能快。**
