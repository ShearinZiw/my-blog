## OSI 七层模型

### **1. 概念**
- OSI（Open Systems Interconnection）由 **ISO** 提出  
- 目标：实现不同厂商设备互联  
- 将网络通信划分为 **7 层**，每层负责特定功能  
- 特点：**分层、独立、协作、模块化**


### **2. 七层模型逐层总结（自下而上）**

#### **① 物理层（Physical Layer）**
**核心职责：传输比特流（0/1）**  
- 定义电气特性、接口规范、信号电压、速率  
- 不关心数据含义，只负责“电信号”传输  

**典型：** 网线、光纤、RJ45、电压电流

#### **② 数据链路层（Data Link Layer）**
**核心职责：将比特流封装成帧，实现相邻节点可靠传输**  
- 差错检测（CRC）  
- 流量控制、帧同步  

**典型：** MAC 地址、以太网、ARP

#### **③ 网络层（Network Layer）**
**核心职责：逻辑寻址 + 路由选择**  
- 决定数据包从源到目的的路径  
- 跨网络转发  

**典型：** IP 地址、IP 协议、路由协议



#### **④ 传输层（Transport Layer）**
**核心职责：端到端通信**  
- 数据分段、重组  
- 提供可靠或不可靠传输  

**典型：** TCP（可靠）、UDP（实时）、端口号



#### **⑤ 会话层（Session Layer）**
**核心职责：建立、管理、终止会话**  
- 会话状态控制  
- 同步、恢复  

**典型：** 会话管理、断点续传（概念）



#### **⑥ 表示层（Presentation Layer）**
**核心职责：数据格式转换**  
- 编码、加密、解密、压缩  
- 屏蔽不同系统的数据表示差异  

**典型：** ASCII、UTF-8、压缩、SSL/TLS（概念上）



#### **⑦ 应用层（Application Layer）**
**核心职责：为用户和应用提供网络服务接口**  
- 定义应用协议  

**典型：** HTTP/HTTPS、FTP、SMTP、DNS、SSH



### **3. OSI 七层模型总结**
1. 分层设计降低复杂度  
2. 每层职责明确  
3. 工程中更常用 TCP/IP，但 OSI 是理论基础  



## TCP/IP 四层模型 — 工程实践模型

### **1. 基本概念**
- 互联网实际使用的模型  
- 比 OSI 更简化、更贴近工程  
- 四层结构：**网络接口层 → 网络层 → 传输层 → 应用层**



### **2. 四层模型逐层总结**



#### **① 网络接口层（Network Interface Layer）**
**核心职责：在物理网络上传输数据**  
- 定义帧格式、MAC、介质访问方式  
- 屏蔽硬件差异  

**典型：**以太网、ARP、MAC 地址



#### **② 网络层（Internet Layer）**
**核心职责：逻辑寻址 + 路由转发**  
- 提供无连接、不可靠的数据报服务  

**典型：**IP、ICMP、路由协议



#### **③ 传输层（Transport Layer）**
**核心职责：端到端通信**  
- 使用端口号区分应用  
- 决定可靠性  
- 实现端到端的通信，保证数据从源主机传到目标主机的应用进程
  - 端口管理：标识不同应用进程​
  - 可靠传输（TCP）：顺序、重传、校验、流量控制​
  - 不可靠快速传输（UDP）：低延迟、广播/组播​
  - 多路复用：一个主机可同时处理多个连接

**典型：**TCP、UDP



#### **④ 应用层（Application Layer）**
**核心职责：为应用提供网络服务**  
- 包含 OSI 的会话层 + 表示层功能  
- 为用户和应用程序提供网络服务接口
- 解决的问题：​
    - a. 定义应用数据格式（如 HTTP、FTP、MQTT）​
    - b.提供不同应用间通信协议（文件传输、远程控制、消息传递）​
    - c.数据表现和语义处理（编码、压缩、序列化等

**典型：**HTTP、FTP、DNS、SMTP、SSH



### **3. OSI vs TCP/IP 对应关系（面试常考表）**

| TCP/IP | 对应 OSI |
|--|--|
| 应用层 | 应用层 + 表示层 + 会话层 |
| 传输层 | 传输层 |
| 网络层 | 网络层 |
| 网络接口层 | 数据链路层 + 物理层 |



### **4. TCP/IP 四层模型总结**
1. 更简洁，贴近实际网络协议  
2. OSI 用于理论，TCP/IP 用于工程  
3. 面试重点：**四层职责 + 典型协议 + 与 OSI 的对应关系**



### 最终总结
- **OSI 七层：物理、链路、网络、传输、会话、表示、应用（自下而上）**  
- **TCP/IP 四层：网络接口、网络、传输、应用**  
- **TCP/IP 应用层 = OSI 的应用 + 表示 + 会话**

## 子网掩码（Subnet Mask）

### **1. 基本概念**
- 子网掩码用于 **划分 IP 地址的网络部分和主机部分**  
- 与 IP 地址配合使用，用来判断：  
  **一台主机属于哪个子网**
- 作用：
  - 网络分段  
  - 提高管理效率  
  - 节省 IP 地址

### **2. 原理（核心机制）**

#### **IP 地址 = 网络号 + 主机号**

#### **子网掩码由连续的 1 和连续的 0 组成：**
- **1 → 网络位**
- **0 → 主机位**

#### **示例解析**

**IP 地址：**192.168.1.10  
**子网掩码：**255.255.255.0  

二进制表示：

| 项目 | 二进制 |
||--|
| IP | 11000000.10101000.00000001.00001010 |
| 掩码 | 11111111.11111111.11111111.00000000 |

计算：

- **网络号 = IP & 子网掩码 = 192.168.1.0**
- **主机号 = IP & (~子网掩码) = 0.0.0.10**

### **3. 子网掩码的功能**

#### **① 区分网络和主机**
- 网络号相同 → 同一子网  
- 网络号不同 → 不同子网

#### **② 划分子网**
- 将大网络拆成多个小子网  
- 提高管理灵活性、减少广播域

#### **③ 确定广播地址**
- **广播地址 = 网络号 + 全 1 的主机位**  
- 用于子网内部广播

### **4. 常用子网掩码（CIDR 表示法）**

| CIDR | 子网掩码 | 主机数量 |
||--|--|
| /24 | 255.255.255.0 | 254 |
| /16 | 255.255.0.0 | 65534 |
| /8 | 255.0.0.0 | 16777214 |

说明：  
**“/24” 表示掩码有 24 位 1**

### **5. 总结**
- **子网掩码用来区分 IP 的网络部分和主机部分**  
- **1 表示网络位，0 表示主机位**  
- **通过子网掩码可以判断 IP 属于哪个子网，并确定广播地址**



## MAC 地址与 IP 地址的区别

### 1. MAC 地址（物理地址）

#### **概念**
- MAC（Media Access Control）地址是 **网卡的物理地址**
- 出厂时由厂家写入，通常不会改变
- **长度：48 位（6 字节）**
- **格式：**`XX:XX:XX:XX:XX:XX`
- **工作层：数据链路层（OSI 第 2 层）**
- **作用：在同一局域网内唯一标识设备**

### 2. IP 地址（逻辑地址）

#### **概念**
- IP 地址是网络中的 **逻辑地址**
- 可由管理员手动配置或由 DHCP 动态分配
- **IPv4：32 位**  
- **IPv6：128 位**
- **工作层：网络层（OSI 第 3 层）**
- **作用：标识设备在网络中的位置，实现跨网络通信**



### 3. MAC vs IP — 核心区别对比

| 对比项 | MAC 地址 | IP 地址 |
|--|-|-|
| 类型 | 物理地址 | 逻辑地址 |
| 长度 | 48 位 | IPv4：32 位；IPv6：128 位 |
| 分配方式 | 厂家烧录 | 手动配置 / DHCP |
| 是否可变 | 基本不变 | 可随网络环境变化 |
| 工作层次 | 数据链路层 | 网络层 |
| 作用范围 | 局域网内唯一标识设备 | 跨网络寻址与路由 |
| 是否可路由 | ❌ 不能跨网段 | ✔️ 可跨网段路由 |
| 示例 | `AA:BB:CC:DD:EE:FF` | `192.168.1.10` |

### 4. MAC 与 IP 在通信中的配合（非常重要）

#### **实际通信流程**
a. 应用层生成数据  
b. 网络层使用 **IP 地址** 确定目标网络  
c. **ARP 将目标 IP → MAC 地址**  
d. 数据链路层使用 **MAC 地址** 完成帧传输  

### **一句话总结：**
> **IP 决定“去哪”，MAC 决定“送给谁”。**

### 5. 嵌入式系统中的实际应用

#### 常见场景
- STM32 + LWIP  
- 工业以太网设备  

#### 常见面试追问

##### ❓ **为什么换 IP 不影响局域网通信？**
- 这个前提不成立：换 IP 会改变本机源地址、子网判断、ARP 邻居项和路由选择，现有 TCP 连接通常也会失效
- MAC 没变只能说明二层接口身份可能没变，不能保证三层 IP 通信继续正常

##### ❓ **为什么不能只用 MAC 地址通信？**
- MAC 地址 **不能跨网段路由**  
- 路由器只看 IP，不看 MAC



### 6. 总结
> **MAC 地址用于局域网内的物理寻址（数据链路层），IP 地址用于跨网络的逻辑寻址（网络层），两者通过 ARP 协同完成通信。**

## TCP 三次握手（Three-way Handshake）

### 1. 基本概念
- TCP 是 **面向连接、可靠传输** 的协议  
- 三次握手用于 **建立连接**  
- 目的：
  1. **确认双方都具备收发能力**  
  2. **同步序列号（ISN）**，保证可靠传输  



### 2. 三次握手过程（逐步解析）

#### **① 客户端 → 服务器：SYN**
- 客户端发送 **SYN** 报文，请求建立连接  
- 报文中包含客户端的初始序列号 **ISN(c)**  
- 服务器收到后，知道客户端想建立连接  



#### **② 服务器 → 客户端：SYN + ACK**
- 服务器回复 **SYN + ACK** 报文  
  - **ACK = ISN(c) + 1**：确认收到客户端的 SYN  
  - **SYN**：服务器也要建立连接，并发送自己的 **ISN(s)**  
- 客户端收到后，知道服务器同意建立连接且具备发送能力  



#### **③ 客户端 → 服务器：ACK**
- 客户端发送 **ACK** 报文  
  - **ACK = ISN(s) + 1**：确认收到服务器的 SYN  
- 至此，连接建立成功，双方进入 **ESTABLISHED** 状态，可以开始数据传输  



### 3. 三次握手关键点（面试必问）

#### **① 为什么需要三次？（可靠性）**
- 确认双方都能 **发送** 和 **接收**  
- 同步双方的 **初始序列号**  
- 防止旧连接报文干扰新连接  



#### **② 状态转换（常考）**
##### 客户端：
- CLOSED → **SYN_SENT** → **ESTABLISHED**

##### 服务器：
- LISTEN → **SYN_RECEIVED** → **ESTABLISHED**



#### **③ 防止旧连接干扰**
- TCP 使用序列号（ISN）区分不同连接  
- 即使旧报文重传，也不会被误认为新连接  



### 4. 总结
> **TCP 三次握手：客户端 SYN → 服务器 SYN+ACK → 客户端 ACK，用于确认双方收发能力并同步序列号，确保可靠通信。**

## 为什么 TCP 需要三次握手，而不是两次

### 背景
TCP 是面向连接、可靠传输的协议。建立连接的核心目标包括：

- 双方都能发送与接收数据  
- 同步双方的初始序列号（ISN），避免旧连接报文干扰新连接  



### 两次握手的问题
假设只进行两次握手：

1. 客户端发送 SYN  
2. 服务器回复 SYN-ACK  
3. 连接直接建立  

这样会产生以下问题：

- 客户端 **无法确认** 服务器的 SYN 是否到达  
- 如果网络中存在 **旧的 SYN-ACK 报文** 被误认为新连接：  
  - 服务器会误以为客户端已确认连接  
  - 客户端实际上并未收到该 SYN-ACK  
  - 可能导致旧连接的数据被误用，造成数据错乱  

两次握手无法确保双方收发能力，也无法避免旧报文干扰。



### 三次握手如何解决问题
第三次握手（客户端发送 ACK）完成了关键确认：

- 客户端确认服务器的 SYN 已成功到达  
- 双方的初始序列号同步  
- 双方都确认自己与对方具备收发能力  
- 避免旧连接报文导致的错误连接  

因此，三次握手是确保 TCP 连接可靠性的最小次数。



### 可优化的机制
- **TCP Fast Open（TFO）**：在握手过程中携带部分数据，减少首包延迟  
- **长连接（Keep-Alive）**：减少频繁建立连接的开销，提高通信效率  



### 总结
三次握手的第三次 ACK 是必不可少的，它确保双方序列号同步、确认收发能力，并防止旧连接报文干扰。两次握手无法满足这些可靠性要求，因此 TCP 必须使用三次握手来建立连接。


## TCP 的四次挥手

### 基本概念
- 四次挥手（Four-way Handshake）是 TCP 断开连接的标准流程  
- 目的是确保双方数据都发送完毕后再关闭  
- TCP 是全双工通信，发送和接收方向独立，因此关闭需要双方分别确认  



### 四次挥手过程
以下假设 **客户端主动关闭**，服务器被动关闭。

#### 第一次挥手（客户端 → 服务器：FIN）
- 客户端发送 FIN，表示“我已经没有数据要发送了”  
- 客户端进入 **FIN_WAIT_1**

#### 第二次挥手（服务器 → 客户端：ACK）
- 服务器收到 FIN 后回复 ACK  
- 服务器进入 **CLOSE_WAIT**  
- 客户端进入 **FIN_WAIT_2**  
- 此时服务器仍可继续发送数据

#### 第三次挥手（服务器 → 客户端：FIN）
- 服务器数据发送完毕后，发送 FIN  
- 服务器进入 **LAST_ACK**

#### 第四次挥手（客户端 → 服务器：ACK）
- 客户端收到 FIN 后发送 ACK  
- 客户端进入 **TIME_WAIT**  
- 服务器收到 ACK 后关闭连接  



### 关键点
#### 全双工通信
- TCP 的发送和接收方向独立  
- 关闭连接需要分别关闭两个方向，因此需要四次挥手  

#### 状态转换
- 客户端：FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED  
- 服务器：CLOSE_WAIT → LAST_ACK → CLOSED  

#### TIME_WAIT 的作用
- 确保服务器收到最后的 ACK  
- 防止旧报文影响后续新连接  



### 总结
TCP 四次挥手通过 FIN 和 ACK 分别关闭双方的发送方向，确保数据传输完整后安全关闭连接。



## 为什么 TCP 断开连接是四次挥手，而不是三次

### 背景
- TCP 是全双工通信：双方都可以独立发送数据  
- 断开连接必须确保双方的数据都发送完毕  
- 与建立连接不同，关闭连接需要分别确认双方的发送方向是否结束  



### 为什么常见抓包是四个报文段

#### 如果只两次挥手
- 客户端发送 FIN，服务器 ACK 后直接关闭  
- 问题：服务器可能还有未发送的数据，直接关闭会导致数据丢失  

被动关闭方收到 FIN 时，应用往往还有数据要发送，所以先单独 ACK，稍后应用 close 再发送 FIN。若它能立即关闭，ACK 与 FIN 可以合并为一个 `FIN, ACK` 报文段，抓包就可能只有三个报文段；客户端仍会用最后一个 ACK 确认该 FIN。



### 两个方向都要独立关闭并被确认
1. 客户端发送 FIN：表示客户端发送方向结束  
2. 服务器 ACK：确认收到客户端的 FIN  
3. 服务器发送 FIN：表示服务器发送方向结束  
4. 客户端 ACK：确认服务器 FIN，双方安全关闭  

由于 TCP 的发送方向是独立的，双方都必须发送 FIN 并收到对方的确认，因此需要四次。



### 总结
TCP 语义上需要双方各发送一个 FIN，并让各自的 FIN 得到确认；“四次挥手”描述的是最常见的四个报文段，不是不可合并的固定最小次数。


## HTTPS 和 HTTP 的区别

### 基本概念
**HTTP（HyperText Transfer Protocol）**  
- 超文本传输协议  
- 数据以 **明文** 方式传输  
- 无加密、无身份验证、无完整性保护  

**HTTPS（HyperText Transfer Protocol Secure）**  
- HTTP 的安全版本  
- 通过 **SSL/TLS** 对数据进行加密  
- 提供数据加密、身份验证、完整性校验  



### HTTP 与 HTTPS 的主要区别
| 项目 | HTTP | HTTPS |
|--|--|--|
| 协议层 | 应用层 | 应用层 + 传输层安全 |
| 传输方式 | 明文 | 加密（SSL/TLS） |
| 安全性 | 易被窃听、篡改、伪造 | 防窃听、防篡改、防伪造 |
| 端口 | 80 | 443 |
| 证书 | 不需要 | 需要 CA 证书 |
| 性能 | 无加密，速度快 | 加密开销略大 |
| 应用场景 | 不敏感数据 | 登录、支付、隐私数据 |



### 工作原理

#### HTTP 工作方式
- 客户端与服务器之间以 **明文** 传输请求和响应  
- 数据容易被窃听、篡改或伪造  

#### HTTPS 工作方式
1. **SSL/TLS 握手阶段**  
   - 服务器向客户端发送 **公钥证书**  
   - 客户端验证证书合法性  

2. **密钥协商阶段**  
   - 现代 TLS（尤其 TLS 1.3）通常使用 (EC)DHE 或 PSK，让双方推导会话密钥，并提供前向保密等属性
   - 证书公钥主要用于验证握手身份/签名，不应把 TLS 一概描述成“客户端生成对称密钥后用 RSA 加密发送”
   - 具体消息、往返次数和算法取决于 TLS 版本、密码套件、会话恢复与传输协议



### 总结
HTTPS 是 HTTP 的加密版本，通过 SSL/TLS 提供加密、身份验证和完整性保护，防止中间人攻击。  
HTTP 为明文传输，安全性较低。



## HTTPS 建连：TCP 与 TLS 是两个不同握手

### 基本概念
- HTTPS = HTTP + SSL/TLS  
- 建立连接需要先完成 **TCP 三次握手**，再进行 **TLS 握手**  
- TLS 握手的目的：验证服务器身份、协商加密算法和密钥  



### TCP 三次握手只是建立可靠字节流
HTTPS 通信首先进行 TCP 三次握手：

#### 第一次握手
客户端发送 SYN，请求建立连接，并生成初始序列号 seq = x。

#### 第二次握手
服务器返回 SYN + ACK，确认客户端序列号 ack = x + 1，并生成自己的序列号 seq = y。

#### 第三次握手
客户端发送 ACK，确认服务器序列号 ack = y + 1，TCP 连接建立。

随后才开始 TLS 握手；TLS 1.2、TLS 1.3、会话恢复以及 HTTP/3 over QUIC 的时序并不相同，因此不存在统一的“HTTPS 三次握手”。



### 总结
HTTPS 在 TCP 连接基础上，通过 TLS 握手建立安全通道，实现服务器身份验证和对称密钥协商，确保数据加密传输的安全性和完整性。


## DNS 解析过程（访问互联网过程、域名解析过程）

### 基本概念
- **DNS（Domain Name System）**：域名系统  
- 功能：将 **域名（www.example.com）→ IP 地址（192.168.1.1）**  
- 目的：让用户使用易记的域名访问互联网，而计算机通过 IP 通信  



### 访问互联网的一般过程
1. 用户在浏览器输入域名  
2. DNS 将域名解析为 IP  
3. 浏览器根据 IP 访问服务器  
4. 建立 TCP / HTTPS 连接  
5. 浏览器发送 HTTP/HTTPS 请求并接收响应  



### DNS 解析过程（递归查询 + 迭代查询）

#### 1. 浏览器缓存查询
- 浏览器先检查自身 DNS 缓存  
- 若命中，直接返回 IP，无需继续查询  

#### 2. 操作系统缓存查询
- 若浏览器无缓存，操作系统检查：  
  - 本地 DNS 缓存  
  - hosts 文件  

#### 3. 递归 DNS 服务器查询
- 操作系统将查询发送给 **本地 DNS 服务器（通常由 ISP 提供）**  
- 若本地 DNS 无缓存，它会代替用户继续向上查询（递归）  

#### 4. 根 DNS 查询
- 本地 DNS 向 **根 DNS** 查询  
- 根 DNS 返回对应顶级域名（TLD）服务器地址，例如：  
  - `.com`  
  - `.cn`  
  - `.org`  

#### 5. 顶级域名（TLD）DNS 查询
- 本地 DNS 向 TLD 服务器查询  
- TLD 返回该域名的 **权威 DNS 服务器** 地址  

#### 6. 权威 DNS 查询
- 本地 DNS 向权威 DNS 查询域名对应的 IP  
- 权威 DNS 返回最终的 IP 地址  

#### 7. 返回客户端
- 本地 DNS 将 IP 缓存，并返回给操作系统  
- 浏览器使用该 IP 发起 TCP/HTTPS 连接访问网站  



### 缓存机制
- **浏览器缓存**：减少重复解析  
- **操作系统缓存**：进一步降低 DNS 查询次数  
- **DNS 服务器缓存**：提高解析速度，减少根/TLD 服务器压力  



### 总结
DNS 解析过程是将域名转换为 IP 的过程，经过浏览器缓存、系统缓存、本地 DNS、根 DNS、TLD DNS、权威 DNS 多级查询，最终得到服务器 IP，从而完成互联网访问。

## ARP（地址解析协议）的工作过程

### 基本概念
- **ARP（Address Resolution Protocol）**：地址解析协议  
- 作用：将 **IP 地址 → MAC 地址**  
- 工作位置：介于 **网络层** 与 **数据链路层** 之间  
- 使用范围：**局域网内** 获取目标设备的 MAC 地址  



### ARP 的工作过程

#### 1. 设备发送 ARP 请求
- 当设备需要向某 IP 发送数据但不知道其 MAC 地址时，会发送 ARP 请求  
- ARP 请求是 **广播包**（广播到局域网所有设备）  
- 包内包含：目标 IP 地址，询问其对应的 MAC 地址  

#### 2. 网络中的设备接收到 ARP 请求
- 局域网内所有设备都会收到该广播  
- 只有 **IP 地址匹配的设备** 才会响应  

#### 3. 目标设备返回 ARP 响应
- 目标设备收到 ARP 请求后，发送 ARP 响应  
- 响应内容包含：目标设备的 **MAC 地址 + IP 地址**  
- ARP 响应是 **单播**，只发给请求设备  

#### 4. 请求设备接收 ARP 响应并缓存
- 请求设备解析出目标 MAC 地址  
- 将 IP–MAC 映射写入 **ARP 表（缓存）**  
- 缓存时间通常为几分钟  

#### 5. 数据发送
- 设备获得 MAC 地址后，即可构造数据帧并发送  
- 后续通信可直接查 ARP 表，无需再次广播  



### ARP 缓存与冲突

#### ARP 缓存
- 存储 IP–MAC 映射  
- 缓存时间一般为 **2–10 分钟**  
- 作用：减少 ARP 广播，提高效率  

#### ARP 冲突
- 若两个设备配置了相同 IP  
- 它们会同时回应 ARP 请求  
- 导致 ARP 表混乱，引发网络通信异常  



### 总结
ARP 通过广播请求、单播响应的方式，将 IP 地址解析为 MAC 地址，并将结果缓存到 ARP 表中，使局域网内的通信能够基于硬件地址顺利进行。

## 如何应对短连接、高并发的场景

### 短连接与高并发的特点
- **短连接**：连接建立快、断开快（如 HTTP 短连接）  
- **高并发**：同一时间大量请求到达  
- **主要问题：**
  - 频繁建立/释放连接导致系统开销大  
  - 文件描述符、端口、内存等资源容易耗尽  
  - 线程/进程频繁创建与切换成本高  



### 使用 I/O 多路复用机制
- 核心思想：**一个线程监听多个 socket**  
- 常见方式：
  - **select**：fd 数量有限，效率低  
  - **poll**：无 fd 限制，但仍是轮询  
  - **epoll（Linux 常用）**：事件驱动、支持高并发、O(1) 事件通知  
- 适用场景：
  - Linux 服务器  
  - 网络服务、嵌入式网关  



### 采用线程池 / 任务队列
- 避免“来一个请求就创建一个线程”  
- 思路：
  - 主线程负责 accept  
  - 工作线程从任务队列取任务处理  
- 优点：
  - 减少线程创建/销毁开销  
  - 控制并发线程数量，防止系统资源耗尽  
- 嵌入式常见：
  - pthread + 任务队列  
  - RTOS 的任务池  



### 使用连接复用或长连接
- 能不用短连接就尽量不用：
  - HTTP Keep-Alive  
  - TCP 长连接  
- 优点：
  - 减少三次握手/四次挥手  
  - 降低 CPU 与网络开销  
- 嵌入式场景：
  - MQTT  
  - 私有 TCP 协议 + 心跳机制  



### 限流与背压机制
- 目的：防止系统过载  
- 常见方式：
  - 限制最大连接数  
  - 限制请求速率（QPS）  
  - 超出部分直接拒绝或丢弃  
- 嵌入式中尤为重要：
  - CPU、内存资源有限  
  - 实时任务不能被拖垮  



### 减少单次请求的处理开销
- 优化方向：
  - 减少动态内存分配（malloc/free）  
  - 使用对象池、内存池  
  - 避免阻塞操作（磁盘、网络）  
- 原则：
  - 请求处理要 **短、快、无阻塞**  



### 总结
通过 **epoll + 线程池 + 长连接 + 限流机制**，可以有效应对短连接和高并发场景，避免频繁创建线程和阻塞 I/O，提高系统吞吐量与稳定性。

## WebSocket 与 Socket 的区别

### 基本概念
**Socket**  
- 底层网络通信接口  
- 可基于 **TCP 或 UDP**  
- 提供进程间或设备间的数据传输能力  
- 属于 **传输层接口**，不是协议  

**WebSocket**  
- 基于 **TCP** 的应用层协议  
- 专为 **浏览器与服务器的全双工通信** 设计  
- 解决 HTTP 只能由客户端发起请求的限制  



### 主要区别
| 对比项 | Socket | WebSocket |
|--|--|--|
| 定义 | 网络通信接口 | 应用层协议 |
| 基于协议 | TCP / UDP | TCP |
| 通信方式 | 全双工，但需自行实现协议 | 原生全双工 |
| 使用场景 | 任意网络程序 | 浏览器实时通信 |
| 建立方式 | 直接建立 TCP/UDP | 需通过 HTTP Upgrade 握手 |
| 数据格式 | 自定义，原始字节流或报文 | WebSocket 帧格式，可文本或二进制 |
| 易用性 | 较复杂，需要自己封协议 | 简单，浏览器原生支持 |



### WebSocket 的优势
1. **全双工通信**：客户端和服务器可随时互发数据  
2. **节省资源**：一次握手后保持连接，避免频繁 HTTP 请求  
3. **实时性高**：适合实时推送，如 IM、行情、游戏同步  



### 总结
Socket 是底层通信接口，可基于 TCP/UDP；WebSocket 是基于 TCP 的应用层协议，专为浏览器与服务器的实时全双工通信设计。



## TCP 的流量控制

### 基本概念
- 流量控制用于 **控制发送端的发送速率**  
- 防止接收端处理不过来导致数据丢失  
- TCP 通过 **窗口机制** 实现流量控制  



### TCP 流量控制的实现机制

#### 1. 接收窗口（Receive Window）
- 接收方在 ACK 中携带 **窗口大小（Window Size）**  
- 表示接收方剩余缓冲区空间  
- 发送方根据窗口大小决定发送量  

#### 2. 滑动窗口机制
- 发送方与接收方维护滑动窗口  
- 随着 ACK 到达，窗口向前滑动  
- 若接收方空间不足，会将窗口缩小，通知发送方暂停发送  

#### 3. 流量控制过程
- 发送方根据窗口大小发送数据  
- 接收方通过调整窗口大小控制发送速率  
- 防止接收方缓冲区溢出  



### 流量控制的特点
- **动态调整**：窗口大小随接收方状态变化  
- **可靠性**：避免接收方溢出导致丢包  
- **与拥塞控制协同**：共同保证网络稳定  



### 总结
TCP 流量控制通过接收窗口和滑动窗口机制控制发送速率，确保接收方不会被大量数据淹没，从而保证可靠传输。



## TCP 的拥塞控制

### 基本概念
- 拥塞控制用于避免网络过载  
- 通过动态调整发送速率，防止网络拥塞导致丢包和性能下降  



### 拥塞控制的四种算法

#### 1. 慢启动（Slow Start）
- 初始拥塞窗口 cwnd = 1 MSS  
- 每收到一个 ACK，cwnd +1  
- 每个 RTT 窗口 **指数增长**

#### 2. 拥塞避免（Congestion Avoidance）
- 当 cwnd 达到阈值（ssthresh）后进入该阶段  
- cwnd 每 RTT **线性增长**，避免过快增加导致拥塞  

#### 3. 快速重传（Fast Retransmit）
- 连续收到 **三个重复 ACK** → 认为丢包  
- 立即重传丢失数据，无需等待超时  

#### 4. 快速恢复（Fast Recovery）
- 在快速重传后，cwnd 减半而不是回到 1 MSS  
- 然后进入拥塞避免阶段  
- 避免过度降低发送速率  



### 拥塞控制过程
- 初始：慢启动，窗口指数增长  
- 达到阈值：进入拥塞避免，窗口线性增长  
- 丢包：触发快速重传 → 快速恢复 → 拥塞避免  



### 总结
TCP 拥塞控制通过慢启动、拥塞避免、快速重传、快速恢复四种算法动态调整发送速率，避免网络拥塞，提高传输效率和稳定性。


## TCP 的粘包和拆包

### 基本概念
- **粘包**：由于 TCP 是**流式协议**，没有消息边界，多个数据包可能被合并在一起发送，接收方无法区分包的边界。  
- **拆包**：一个完整的数据包被拆成多段接收，导致接收方无法一次性获取完整消息。



### 粘包的原因

#### 1. TCP 是流式协议
- TCP 以字节流方式传输数据，不关心消息边界  
- 应用层连续发送多个小包时，TCP 可能将它们合并成一个大包发送  

#### 2. 发送方发送过多小数据
- 多个小包在 TCP 缓冲区中被合并，形成粘包  

#### 3. 网络延迟与缓冲区机制
- 网络延迟、缓冲区未及时刷新等情况也会导致多个包被合并  



### 拆包的原因

#### 1. 数据包大小不一致
- TCP 会根据 MTU（最大传输单元）对数据进行分段  
- 若应用层发送的数据超过 MTU，会被拆成多个 TCP 段  

#### 2. TCP 分段机制
- TCP 会根据网络状况动态调整发送数据量  
- 大包可能被拆分成多个小段发送  



### 解决粘包和拆包的常用方法

#### 1. 固定长度包
- 每个数据包长度固定  
- 接收方按固定长度读取  
- 缺点：不灵活，浪费带宽  

#### 2. 特殊分隔符
- 在每个包尾部添加特定分隔符（如 `\n`、`\r\n`）  
- 接收方根据分隔符拆分消息  
- 常用于文本协议  

#### 3. 包头定义长度（最常用）
- 在包头添加 **长度字段**，指明数据区长度  
- 接收方先读包头，再按长度读取数据  
- 常见于 HTTP、FTP、自定义协议  

#### 4. Nagle 算法
- 合并小包，减少频繁发送  
- 适用于减少小包导致的粘包，但不解决拆包问题  



### 总结
TCP 是流式协议，没有消息边界，因此会出现粘包和拆包。常见解决方案包括固定长度、分隔符、包头长度字段等方式，由应用层自行定义协议来确保消息边界清晰。

## 什么是 Socket

### Socket 的本质
- Socket 是 **操作系统提供的网络通信机制**  
- 位于 **应用层 与 传输层（TCP/UDP）之间**  
- 应用程序通过 Socket 使用网络，而无需直接操作底层协议  
- 可以理解为：**程序访问网络的“插口”**


### Socket 通信的基本要素
一次完整的 Socket 通信至少需要：

1. **IP 地址**：定位主机  
2. **端口号**：定位主机上的具体进程  
3. **协议类型**：TCP 或 UDP  

常说的 **五元组**（唯一标识一个 TCP 连接）：

```
源 IP、源端口、目的 IP、目的端口、协议
```


### Socket 的常见类型

#### TCP Socket
- 面向连接  
- 可靠传输（确认、重传、排序）  
- 典型应用：HTTP/HTTPS、FTP、SSH  
- 特点：
  - 需要三次握手  
  - 数据以字节流方式传输  

#### UDP Socket
- 无连接  
- 不保证可靠性  
- 速度快、开销小  
- 典型应用：视频/语音、DNS、实时通信  
- 特点：
  - 一次发送一个数据包  
  - 可能丢包、乱序  


### Socket 通信的基本流程（以 TCP 为例）

#### 服务器端
1. `socket()` —— 创建套接字  
2. `bind()` —— 绑定 IP 和端口  
3. `listen()` —— 监听连接  
4. `accept()` —— 接受客户端连接  
5. `recv()/send()` —— 数据通信  

#### 客户端
1. `socket()`  
2. `connect()` —— 连接服务器  
3. `send()/recv()` —— 数据通信  


### Socket 与嵌入式 / Linux 的关系
在嵌入式 Linux 或 RTOS + TCP/IP 协议栈中：

- Socket 是统一的网络编程接口  
- 底层可能是：
  - **lwIP**（STM32 + FreeRTOS）  
  - **Linux 内核网络栈**  

典型应用：
- 设备与上位机通信  
- 嵌入式设备联网  
- OTA 升级  


### 总结
Socket 是操作系统提供的网络通信接口，应用程序通过 Socket 使用 TCP/UDP 协议，实现不同设备或进程之间的网络数据通信。


## Socket 网络编程

### 基本概念
- Socket 是网络通信的端点  
- 网络编程：通过 Socket API 实现客户端与服务器之间的数据传输  
- 支持 TCP（面向连接）和 UDP（无连接）两种方式  


### Socket 编程的步骤

#### 1. 创建套接字（socket）
使用 `socket()` 创建套接字，指定协议类型（TCP/UDP）。

#### 2. 绑定套接字（bind）
服务器端将套接字绑定到指定 IP 和端口。

#### 3. 监听连接（listen）
服务器调用 `listen()` 等待客户端连接。

#### 4. 接受连接（accept）
服务器使用 `accept()` 接受客户端请求，返回新的通信套接字。

#### 5. 客户端连接服务器（connect）
客户端使用 `connect()` 主动连接服务器。

#### 6. 数据传输（send/recv）
双方使用 `send()`、`recv()` 或 `write()`、`read()` 进行数据交换。

#### 7. 关闭连接（close）
通信结束后调用 `close()` 释放资源。


### TCP 编程示例
![TCP](/img/d9e2203b-b485-4511-9cab-984bbce29586.png)

- 服务器端：`socket → bind → listen → accept → recv/send`  
- 客户端：`socket → connect → send/recv`  

#### 服务器

```c
#include <stdio.h>​
#include <string.h>​
#include <arpa/inet.h>​
#include <unistd.h>​
​
int main() {​
    int sockfd, client_sock;​
    struct sockaddr_in server_addr, client_addr;​
    char buffer[1024];​
    socklen_t client_len = sizeof(client_addr);​
​
    sockfd = socket(AF_INET, SOCK_STREAM, 0);​
    if (sockfd == -1) {​
        perror("Socket creation failed");​
        return -1;​
    }​
​
    server_addr.sin_family = AF_INET;​
    server_addr.sin_port = htons(8080);​
    server_addr.sin_addr.s_addr = INADDR_ANY;​
​
    bind(sockfd, (struct sockaddr*)&server_addr, sizeof(server_addr));​
    listen(sockfd, 5);​
​
    printf("Server is listening on port 8080...\n");​
​
    client_sock = accept(sockfd, (struct sockaddr*)&client_addr, &client_len);​
    if (client_sock == -1) {​
        perror("Client connection failed");​
        return -1;​
    }​
​
    ssize_t n = recv(client_sock, buffer, sizeof(buffer) - 1, 0);​
    if (n > 0) {​
        buffer[n] = '\0';​
        printf("Received message: %s\n", buffer);​
    } else if (n < 0) {​
        perror("recv failed");​
    }​
​
    close(client_sock);​
    close(sockfd);​
​
    return 0;​
}
```

#### 客户端

```c
#include <stdio.h>​
#include <string.h>​
#include <arpa/inet.h>​
#include <unistd.h>​
​
int main() {​
    int sockfd;​
    struct sockaddr_in server_addr;​
    char message[] = "Hello, Server!";​
​
    sockfd = socket(AF_INET, SOCK_STREAM, 0);​
    if (sockfd == -1) {​
        perror("Socket creation failed");​
        return -1;​
    }​
​
    server_addr.sin_family = AF_INET;​
    server_addr.sin_port = htons(8080);​
    server_addr.sin_addr.s_addr = inet_addr("127.0.0.1");​
​
    connect(sockfd, (struct sockaddr*)&server_addr, sizeof(server_addr));​
​
    send(sockfd, message, strlen(message), 0);​
    printf("Message sent: %s\n", message);​
​
    close(sockfd);​
​
    return 0;​
}
```

### UDP 编程示例
UDP 无需连接：

- 服务器端：`socket → bind → recvfrom`  
- 客户端：`socket → sendto`  


### 总结
Socket 网络编程通过创建、绑定、监听、连接、发送和接收数据，实现客户端与服务器之间的通信。  
TCP 使用流式、可靠连接；UDP 使用无连接、快速传输。


## 多线程 Socket 编程中如何避免线程安全问题

### 基本概念
在多线程环境中，多个线程可能同时访问同一个 Socket 或共享数据，如果没有同步机制，就会出现：

- 数据竞争  
- 数据错乱  
- 死锁  

因此，多线程 Socket 编程必须保证线程安全，确保通信的正确性与稳定性。


### 常见的线程安全问题

#### 1. 共享资源竞争
多个线程同时读写同一个 Socket 或共享变量，会导致状态不一致。

#### 2. 数据错乱
多个线程同时向同一个 Socket 写数据时，数据可能交叉、覆盖或丢失。

#### 3. 死锁
不正确使用锁可能导致线程相互等待，程序无法继续执行。


### 避免线程安全问题的方法

#### 1. 使用互斥锁（Mutex）
- 最常用的同步方式  
- 确保同一时间只有一个线程访问共享 Socket  
- 避免多个线程同时写入导致数据混乱  

示例（伪代码）：

```c
pthread_mutex_t lock;

void* thread_func(void* arg) {
    pthread_mutex_lock(&lock);
    send(socket_fd, data, len, 0);
    pthread_mutex_unlock(&lock);
    return NULL;
}
```


#### 2. 每个线程独立使用自己的 Socket
- 最彻底的线程安全方式  
- 每个线程处理一个客户端连接，互不干扰  
- 服务端常见模式：**一个客户端一个 Socket，一个线程处理一个客户端**


#### 3. 使用线程池 + 工作队列
- 主线程负责 accept  
- 将任务（socket_fd）放入队列  
- 工作线程从队列中取任务处理  
- 避免频繁创建线程，提高性能  

示例（伪代码）：

```c
void* worker(void* arg) {
    while (1) {
        task_t task = get_task_from_queue();
        process_socket_request(task.socket_fd);
    }
}
```


#### 4. 使用原子操作
- 对共享变量使用原子操作，避免竞争  
- 适用于计数器、状态标志等简单共享数据  

示例：

```c
atomic_int counter;

void* thread_func(void* arg) {
    atomic_fetch_add(&counter, 1);
    return NULL;
}
```


#### 5. 无锁设计（Lock-Free）
- 使用无锁队列、无锁环形缓冲区等结构  
- 提高性能，减少锁开销  
- 适用于高并发、高性能场景  
- 设计复杂，需要谨慎使用  


### 避免死锁

#### 1. 统一加锁顺序
所有线程必须按照相同顺序获取多个锁，避免循环等待。

#### 2. 使用超时锁
加锁失败后可退出或重试，避免无限等待。

#### 3. 避免嵌套锁
减少在持有一个锁时再申请另一个锁的情况。


### 总结
多线程 Socket 编程中常见的线程安全策略包括：

- 使用互斥锁保护共享 Socket  
- 为每个线程分配独立 Socket  
- 使用线程池管理任务  
- 使用原子操作减少竞争  
- 在高性能场景中采用无锁设计  

通过这些方法，可以有效避免数据竞争、数据错乱和死锁，提高系统的稳定性与并发能力。

## 以太网协议栈

### 基本概念
- **以太网（Ethernet）**：一种局域网（LAN）技术，工作在 **物理层 + 数据链路层**  
- **协议栈**：按 OSI 模型分层，每层负责不同通信任务  
- 以太网协议栈主要涉及：物理层、数据链路层、网络层、传输层、应用层  


### 以太网协议栈的层次

#### 1. 物理层（Physical Layer）
- 协议：10BASE‑T、100BASE‑TX、1000BASE‑T 等  
- 功能：
  - 定义电缆、信号、电气特性  
  - 负责比特流的发送与接收  


#### 2. 数据链路层（Data Link Layer）
- 协议：Ethernet、MAC  
- 功能：
  - **MAC 地址**：唯一的 48 位物理地址  
  - **帧结构**：封装数据为以太网帧  
  - **错误检测**：CRC 校验  
  - **介质访问控制**：控制共享介质上的通信  

以太网帧格式：
- 目的 MAC（6 字节）  
- 源 MAC（6 字节）  
- 类型（2 字节）  
- 数据（46–1500 字节）  
- CRC 校验（4 字节）  


#### 3. 网络层（Network Layer）
- 协议：IP  
- 功能：
  - **IP 地址**：标识网络中的主机  
  - **路由**：跨网络转发数据  
  - IP 数据包包含源 IP、目的 IP、数据等  


#### 4. 传输层（Transport Layer）
- 协议：TCP、UDP  
- 功能：
  - **TCP**：面向连接、可靠、有序  
  - **UDP**：无连接、高效、可能丢包  


#### 5. 应用层（Application Layer）
- 协议：HTTP、FTP、SMTP、DNS 等  
- 功能：为用户提供网络服务接口  


### 以太网协议栈的流程
1. **应用层**：生成数据（如 HTTP 请求）  
2. **传输层**：TCP/UDP 分段并加头部  
3. **网络层**：封装 IP 包，加入源/目的 IP  
4. **数据链路层**：封装以太网帧，加 MAC 地址与 CRC  
5. **物理层**：将帧转换为电信号发送  
6. **接收端**：逐层解包，最终交给应用层  


### 总结
以太网协议栈通过物理层、数据链路层、网络层、传输层、应用层的分层设计，实现了从应用数据到物理信号的完整通信过程。物理层与链路层负责局域网传输，网络层负责跨网路由，传输层保证可靠性。


## 网络通信中如何保证数据安全

### 机密性（Confidentiality）
目标：防止数据被未授权读取  
方法：
- **加密传输**  
  - 对称加密：使用经过评审的现代 AEAD 方案（例如 AES-GCM 或 ChaCha20-Poly1305），避免 DES 等已淘汰算法
  - 非对称加密：RSA、ECC  
- **VPN / TLS/SSL**  
  - 建立安全隧道（HTTPS、MQTT over TLS）  


### 完整性（Integrity）
目标：防止数据被篡改  
方法：
- 对抗主动攻击需要 MAC（如 HMAC）、AEAD 或数字签名；普通哈希本身不认证来源
- CRC、互联网 checksum 只能检测偶发传输损坏，不提供安全完整性
- MD5 已不适合作为现代安全完整性方案；算法和密钥管理应采用成熟协议（如 TLS）


### 认证（Authentication）
目标：确认通信双方身份  
方法：
- 用户名/密码  
- X.509 证书（TLS）  
- Token、HMAC、JWT（适合嵌入式）  


### 防重放攻击（Replay Attack）
目标：防止攻击者重复发送旧数据包  
方法：
- 时间戳 + 有效期  
- 随机数（Nonce）  
- 序列号检测  


### 网络层安全策略
- 防火墙、访问控制  
- IDS/IPS 入侵检测与防护  
- 网络分段隔离关键设备  


### 总结
网络通信安全依赖多层防护：  
- **加密**保证机密性  
- **哈希/签名**保证完整性  
- **认证机制**确认身份  
- **序列号/时间戳**防重放  
- **防火墙/访问控制**提供外围安全  

这些机制共同确保数据在网络中的安全传输。
