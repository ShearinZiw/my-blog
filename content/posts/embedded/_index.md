# 嵌入式五条技术主干

这里不是把面试答案按名词堆在一起，而是沿着真实产品的数据与控制路径组织知识：

`C 源码 → ELF/固件 → MCU 外设 → RTOS 任务 → Linux/驱动 → lwIP 网络`

每条主干都按同一套方式展开：

1. **先给结论**：能在 30 秒内回答基础题；
2. **再讲机制**：能解释为什么，不靠背关键词；
3. **落到项目**：能说明约束、取舍、指标和验证方法；
4. **进入排障**：能从现象收集证据，而不是凭感觉改代码。

## 推荐学习顺序

- **准备 MCU / IoT 岗**：C 工具链 → MCU → RTOS → lwIP → Linux / 驱动。
- **准备 Linux BSP / 驱动岗**：C 工具链 → Linux / 驱动 → MCU → 网络基础 → lwIP。
- **准备 Connectivity 岗**：网络基础 → lwIP → RTOS → MCU → [乐鑫 Connectivity]({{< relref "../company/espressif-connectivity.md" >}})。
- **已有项目、准备投递**：先从故障现象进入对应主干，再回补原理；每个项目至少准备一条量化指标与一次闭环排障。

## 一道题的四层回答法

以“中断里能不能加锁”为例：

1. **结论层**：不能使用可能睡眠的锁；能否使用自旋/临界区还取决于平台与上下文。
2. **机制层**：中断上下文没有可被调度睡眠的任务语义，持锁者还可能被当前中断打断。
3. **工程层**：ISR 只采样、清中断、投递事件；耗时工作延后到任务或 workqueue。
4. **诊断层**：记录 IRQ 时长、嵌套、锁依赖与调度延迟，用 trace 证实而不是猜测。

## 项目经历最小证据集

每个项目都补齐下面六项，才能从“做过”升级为“能追问”：

- **约束**：Flash/RAM、周期、吞吐、功耗、启动时间或成本上限；
- **职责**：你负责的边界，不把团队成果全部写成个人成果；
- **方案**：至少一个被放弃的备选方案和放弃原因；
- **难点**：一个可复现的真实故障，而不是“时间紧”；
- **证据**：日志、抓包、Map、示波器、trace、压力测试数据；
- **结果**：优化前后同口径指标，以及回归验证范围。
